# 하이디 능력 — 뿌요 (설계)

> **설계 문서다. 코드도 에셋도 만들지 않았다.** composer(w8)의 시트가 오면 구현한다.
> 참조 원화: `C:\Users\user\OneDrive\바탕 화면\똥\뿌요.jpg` (하얀 말티푸, 귀만 크림색)

## 0. 한 줄 요약

하이디의 강아지 **뿌요**가 땅에서 혼자 돌아다니다가, **60점마다 웅크렸다가
먼 쪽으로 뛰어올라 회오리를 치며 날아간다.** 지나간 길의 일반 똥이 빨려 들어간다.

선례: **태이**(`KAbility.ts`)가 동반자 배회의 선례, **참새**(`RedAbility.ts`)가
발사 시 시트 교체·방향 판단의 선례다. 둘 다에서 겪은 함정을 아래에 반영했다.

## 1. 상태 기계

```
                    ┌──────────────── 착지 ────────────────┐
                    ↓                                      │
   [walk] ⇄ [idle] ──60점 마일스톤──> [crouch] ─> [jump] ─> [spin]
     ↑                                   220ms     160ms    비행 중
     └── 경계에서 방향 반전 (태이와 같다)
```

| 상태 | 하는 일 | 빠져나가는 조건 |
|---|---|---|
| `walk` | 좌우 왕복. 경계 여백에서 반전 | 마일스톤 / 가끔 `idle` |
| `idle` | 제자리에서 숨쉬기. 걷기만 하면 기계처럼 보인다 | `puyoIdleMs` 경과 |
| `crouch` | **예비 동작.** 몸을 낮추고 날아갈 방향을 본다 | `puyoCrouchMs` 경과 |
| `jump` | 발을 떼고 솟는다. 발밑에 흙먼지 한 줌 | `puyoJumpMs` 경과 |
| `spin` | **회오리 비행.** 포물선으로 먼 쪽까지 | 착지점 도달 |
| (착지) | 흙먼지 + 짧은 `crouch` 1프레임 → `walk` | 즉시 |

### 왜 `crouch` 를 따로 두는가 · 몇 ms 인가

점수 도달 즉시 날아가면 **예비 동작이 죽는다** — 관객이 "무슨 일이 일어났다"를
인지하기 전에 끝난다. 이 저장소의 선례:

| | 예비 동작 | 본동작 |
|---|---|---|
| 로봇 (레드) | `robotRaiseMs` **260ms** | 베기 180ms |
| 큐브 (테드, 옛) | 충전 ~600ms | 파열 |
| 티라노 (레드) | 걸어오기 900ms | 포효 520ms |

뿌요는 **작고 빠른 동물**이라 로봇만큼 뜸들이면 굼떠 보인다.
→ `puyoCrouchMs: 220` 을 시작값으로 제안한다. `jump` 는 **160ms** (발 떼고 솟는 구간),
`spin` 은 거리에서 계산한다(아래).

### 마일스톤이 겹칠 때 — 삼킨다

`crouch`/`jump`/`spin` 중에 마일스톤이 또 오면 **무시한다**
(레드가 `finishing` 중 발사를 막는 것과 같다). 안 그러면 큰 보너스 한 번에
뿌요가 여러 마리로 갈라진다. 상태 하나만 보면 되므로 별도 플래그가 필요 없다.

## 2. "멀리 있는 쪽" — **화면 중앙 기준**으로 고른다

뿌요의 x 가 화면 중앙보다 왼쪽이면 오른쪽으로, 오른쪽이면 왼쪽으로 난다.
정확히 가운데면 **지금 걷던 방향**으로 (갑자기 반대로 꺾이면 부자연스럽다).

**플레이어 기준을 안 쓰는 이유**: 뿌요는 태이처럼 **플레이어와 무관하게** 배회한다.
플레이어 기준으로 잡으면 플레이어가 뿌요 옆에 서 있을 때 비행 거리가 0 에 가까워져
연출이 통째로 뭉개진다. 화면 중앙 기준이면 **비행 거리가 항상 `W/2 - 여백` 이상**으로
보장되고, 보는 사람이 "먼 쪽으로 간다"를 예측할 수 있다.

착지점: `puyoLandMargin` 만큼 화면 안쪽. 화면 밖으로 나갔다 돌아오게 하지 않는다 —
**뿌요는 상시 화면에 있어야 한다**(태이와 같은 규칙). 사라졌다 나타나면
"동반자가 늘 함께 있다"는 읽기가 깨진다.

비행 궤적: **포물선**. 정점 높이 `puyoArcH`(화면 높이 대비), 수평은 등속.
`jump` 의 솟는 구간과 `spin` 의 포물선이 이어지도록 시작 기울기를 맞춘다.

## 3. 회오리 — **새 시트를 굽지 않는다 (1안)**

CLAUDE.md 이펙트 화풍: **오브젝트는 하드 엣지, 기류는 부드럽게.**
회오리는 기류다 → 부드럽게. 뿌요 본체는 시트 그대로 하드 엣지.

### 색이 가장 큰 제약이다

**뿌요가 흰색이다.** 흰 회오리를 얹으면 개가 사라진다. 게다가 밝은 배경
(`background2` 평균 192/255)에서 가산 흰색은 아무 일도 안 일어난 것처럼 보인다 —
테드 파동에서 이미 겪은 함정이다.

→ 파동과 같은 처방: **단면을 `어두운 테두리 → 밝은 코어 → 어두운 테두리`** 로 잡고
**일반 블렌드**로 얹는다. 밝은 데선 테두리가, 어두운 데선 코어가 형태를 잡는다.
거기에 **차가운 회색-청색 색조**를 살짝 얹어 크림색 개와 색으로도 갈린다.

### 1안 (권장) — 기존 텍스처 조립, **VRAM 0**

이미 preload 된 `fx_proc_ring`(소프트 링) + `fx_proc_streak`(가로 줄기)만 쓴다.

| 층 | 텍스처 | 개수 | 하는 일 |
|---|---|---|---|
| 깔때기 | `fx_proc_ring` | 5 | 세로로 쌓고 `setScale(sx, sy)` 로 **납작한 타원**. 위로 갈수록 크고 옅게 |
| 소용돌이 | `fx_proc_streak` | 6 | 깔때기 축을 타원으로 공전. `x = cx + cos(φ)·r`, 뒤쪽(φ 뒤편)은 축소+감알파 |
| 먼지 | `burst('smoke')` | 이륙·착지 각 1회 | 발 떼는 순간과 닿는 순간에만 |

**회전을 파는 건 공전하는 줄기다.** 대칭인 링을 돌려 봐야 안 보인다 — 참새 궤도에서
앞뒤 원근(`orbitBackScale`/`orbitBackAlpha`)을 쓴 것과 **같은 구조**를 세로축으로 돌린다.
줄기는 소프트 텍스처라 임의 각도로 돌려도 안 뭉갠다.

- 스프라이트 11장을 **비행 중에만** 매 프레임 갱신한다 (파티클 이미터가 아니다 →
  `EMITTER_MAX 14` 를 안 먹는다)
- **뿌요 본체는 절대 돌리지 않는다.** 회전은 `spin` 시트가 이미 담고 있다
  (픽셀 오브젝트를 임의 각도로 돌리면 뭉개진다 — 테드 말 퍼짐에서 같은 이유로 회전을 뺐다)
- depth: 회오리 뒤층 → 뿌요 → 회오리 앞층 순으로 **개를 감싸야** 회오리 '안'에 있어 보인다

### 2안 (1안이 검수에서 실패하면) — 절차 생성 시트 `puyoVortex`

`cubeWave` 와 같은 방식. 96×128 × 8프레임 = **0.39MB**, 캔버스 한 번 구워
루프 재생. 1안보다 형태를 정교하게 잡을 수 있지만 VRAM 이 0 이 아니고,
**굽는 비용을 preload 로 밀어야 한다**(`FX_WARM_GROUPS` — 발동 프레임에 구우면
그 프레임이 통째로 밀린다. 테드 파동에서 실제로 그랬다).

### 판단 순서

`scripts/fx-wave-preview.ts` 와 같은 **미리보기 하네스**로 1안을 실제 게임 표시
크기로 뽑아 보고 결정한다. 브라우저 없이 PNG 로 낼 수 있다.
**밝은 배경·어두운 배경 둘 다** 검수한다 (파동 때와 같은 절차).

## 4. 똥 상호작용 — 제안

### 제안: **회오리 경로의 일반 똥을 빨아들여 제거, 개당 20점**

| 능력 | 간격 | 점/개 | 범위 |
|---|---|---|---|
| 레드 참새 | 50점 | 15 | 위로 직선, **1개만** |
| 테드 말 낙하 | 60점 | 20 | 낙하 경로 |
| **뿌요 회오리 (제안)** | **60점** | **20** | **비행 경로** |
| 레드 티라노 | 마무리 | 25 | 화면 폭 78% 원 |
| 로봇 | 마무리 | 30 | 화면 전체 |
| K 빔 | 마일스톤 | 50 | 화면 세로 |

**20점인 근거**: 간격(60점)과 경로형이라는 점이 테드와 같다. 뿌요가 더 센 자리에
있는 건 점수가 아니라 **자동으로 계속 돈다**는 것이다 — 테드는 말이 쌓여야 하고
레드는 참새를 다 써야 마무리가 나오는데, 뿌요는 조건 없이 60점마다 난다.
거기에 점당 보상까지 얹으면 SR 하나가 혼자 앞선다.

**판정**: 테드의 `smashPoops` 와 같은 **점-선분 거리 판정**을 그대로 쓴다
(한 프레임에 수십 px 을 움직이므로 현재 위치만 보면 뚫고 지나간다 — 터널링).
반경은 회오리 반폭 ≈ `puyoHitR: 34` 를 시작값으로 제안(회오리가 개보다 넓다).

**특수 똥은 구조적으로 안 지워진다** — `api.poops` 가 일반 똥 전용 그룹이다.
금·다이아·토파즈·무지개는 플레이어가 먹어야 하는 보너스라 없애면 뺏는 것이 된다.

**재진입 가드 (필수)**:
```ts
this.lastPuyoScore += bonus;   // 먼저
api.addAbilityBonus(bonus);    // 나중
```
`addAbilityBonus` 는 GameScene 안에서 점수를 1점씩 순회하며 마일스톤을 부른다.
가드 없이 주면 그 줄이 곧바로 다음 비행을 부른다. 상태 기계가 `spin` 중 마일스톤을
삼키긴 하지만, **착지하는 순간 대기하던 마일스톤이 터진다** — 점수 가드가 따로 필요하다.
(테드·K·레드가 전부 같은 자리에서 두 번 터졌다.)

### 대안 둘 (고르면 그쪽으로 간다)

- **(가) 점수 없이 제거만** — 순수 유틸. 하이디가 "치우는 캐릭터"가 된다
- **(나) 빨려 들어가는 연출 추가** — 똥이 회오리 중심으로 120ms 빨려 들다 사라진다.
  "회오리"가 훨씬 잘 읽히지만 똥마다 트윈 상태가 생긴다. 한 번에 10개 넘게 걸리면
  비용이 붙으므로 **하네스로 재고 나서** 켠다

### 타격 이펙트는 시끄럽게? 조용히?

경로형이라 몇 개씩 걸리므로 **개당 타격 이펙트(`recycle()` 기본)** 가 맞다(테드와 같다).
다만 **한 프레임에 6개를 넘으면** 공통 상한(`impactHit maxConcurrent 6`)에 걸려
슬롯 경쟁만 생긴다 → 하네스로 재서 넘으면 `recycle(true)` + 요약 이펙트 하나로 바꾼다.
**이건 구현 전 측정으로 정한다.**

## 5. 성능

**뿌요는 상시 화면에 있다.** 태이와 같은 조건이므로 상시 비용을 먼저 따진다.

| | 상시 (walk/idle) | 비행 중 (spin, ~0.7초) |
|---|---|---|
| 스프라이트 | 1 (뿌요) | 1 + 회오리 11 |
| 매 프레임 계산 | 경계 반전 + 방향 판정 | 포물선 + 회오리 11장 위치 + **거리 판정 최대 60회** |
| 파티클 이미터 | 0 | 이륙·착지 각 1회 (일회성) |

**거리 판정은 회오리 1개 × 똥 최대 60개 = 60회/프레임.** 테드의 퍼짐이
말 10개 × 60 = **600회/프레임**에 `onUpdate` p50 **0.009ms** 였으므로
뿌요는 그 1/10 이다. 문제가 될 수 없다 — 다만 **재고 나서 보고한다.**

주의할 곳:
- 방향 전환은 **진행 방향**으로 판단한다. 참새에서 `setFlipX(cos > 0)` 로
  **있는 자리**를 보다가 절반 구간에서 뒤로 나는 그림이 나왔다. 속도 부호를 본다
- 좌우 반전 경계에서 **히스테리시스** — 속도가 0 에 가까운 순간 부호가 떨면 깜빡인다
  (참새는 `FLIP_DEADZONE 0.06`)
- 회오리 11장은 **비행이 끝나면 전부 회수**한다. 하네스 `[R]` 계열처럼
  종료 후 `sprites=0` 을 못박는다
- 시트 교체 시 `startFrame` — **Phaser 의 `currentFrame.index` 는 1부터다.**
  그대로 넣으면 마지막 프레임에서 `frames[n]` 이 undefined 라 게임이 죽는다
  (참새에서 실제로 터졌다)

## 6. VRAM

composer 가 5개 파일로 주면:

| | 크기 |
|---|---|
| 5파일 × 128×128 × 4프레임 (512×128) | 0.25MB × 5 = **1.25MB** |

**한 장짜리 가로 스트립으로 받는 편이 낫다** (아래 composer 조건 참고):

| | 크기 |
|---|---|
| 1파일 × 128×128 × 16프레임 (2048×128) | **1.00MB** |

**전부 preload 한다.** 뿌요는 `onCreate` 부터 화면에 있고 60점에 바로 날아가므로
지연 로딩할 구간이 없다. 하이디를 고른 판에서만 올라간다
(`character.ts` 의 `extraFxSheets` → 그 배열 상수는 `abilityParams.ts` 에 둔다.
레드가 그렇게 해서 **`character.ts` 를 안 건드리고** 시트를 늘렸다).

회오리는 **1안이면 0MB**, 2안이면 +0.39MB.

### 어느 로딩 경로를 쓰는가 — **FX 시트 경로** (참새와 같다)

`charAnim.ts` 의 `CharAnimName` 은 `'idle' | 'walk' | 'hit'` 뿐이다.
뿌요는 `crouch`/`jump`/`spin` 이 더 필요하므로 그 공용 타입을 넓히면
전 캐릭터에 영향이 간다. 참새·체스말이 쓰는 **`loadFxPickSheet` + 능력이 직접
애니 등록**하는 길로 간다 (`RedAbility.registerAnims` 와 같은 구조).

## 7. composer 에게 요구할 조건 (w1 전달용)

**A. 파일 — 한 장짜리 가로 스트립 하나**
- `puyo_left_128x128.png`, **2048×128** (128×128 프레임 16장, 가로 한 줄)
- 프레임 순서 **고정**: `idle 0-1` · `walk 2-7` · `crouch 8-9` · `jump 10-11` · `spin 12-15`
- 왼쪽만. 오른쪽은 코드가 뒤집어 쓴다
- 5개 파일보다 **한 장이 낫다** — 로딩 실패 지점이 1/5 로 줄고 VRAM 도 1.25 → 1.00MB

**B. 프레임 안 배치 — 제일 중요하다**
- **몸통 중심이 모든 프레임에서 같은 자리**여야 한다. 회오리가 몸통을 감싸므로
  프레임마다 중심이 흔들리면 회오리가 개에서 미끄러진다
  (참새 위 보는 시트에서 같은 조건을 걸었고, 안 맞았으면 전환에서 튀었다)
- `spin` 은 **몸을 웅크려 공처럼 만 상태**로 4프레임이 **매끄럽게 순환**해야 한다
  (비행 내내 반복 재생된다 — 첫 프레임과 마지막 프레임이 이어져야 한다)
- `crouch` 는 눌린 자세, `jump` 는 뻗은 자세. 둘의 실루엣이 확실히 달라야
  예비 동작이 읽힌다

## 똥 상호작용 — 경로의 일반 똥 제거, **20점/개**

| 능력 | 간격 | 점/개 |
|---|---|---|
| 레드 참새 | 50 | 15 (한 번에 1개) |
| **테드 말 낙하** | **60** | **20** (경로형) |
| **뿌요 회오리 (채택)** | **60** | **20** (경로형) |
| 레드 티라노 / 로봇 | 마무리 | 25 / 30 |
| K 빔 | 마일스톤 | 50 |

간격(60점)도 경로형이라는 점도 테드와 같아서 같은 값으로 맞췄다. 뿌요가 더 센 자리에
있는 건 점수가 아니라 **조건 없이 자동으로 계속 돈다**는 것이다 — 테드는 말이 쌓여야
하고 레드는 참새를 다 써야 마무리가 나온다. 거기에 점당 보상까지 얹으면 SR 하나가
혼자 앞선다.

판정은 테드 낙하와 같은 **점-선분 거리 판정**(반경 34px)이다. 한 프레임에 수십 px 을
움직이므로 현재 위치만 보면 뚫고 지나간다. 특수 똥은 `api.poops` 가 일반 똥 전용
그룹이라 **구조적으로** 안 닿는다.

**재진입 가드**: `lastFireScore += bonus` 를 먼저, `addAbilityBonus` 를 나중에.
상태 기계가 비행 중 마일스톤을 삼키긴 하지만 **착지하는 순간 대기하던 마일스톤이
터지므로** 점수 가드가 따로 필요하다. 실측: 마일스톤 3회 중 발동 1회(연쇄 0).

## 회오리 — 설계대로 코드로

- 깔때기: `fx_proc_ring` 7장을 납작한 타원으로 쌓는다. **아래가 좁고 위가 넓다**
  (부호를 뒤집었다가 위아래가 뒤집힌 깔때기가 나와 고쳤다)
- 소용돌이: `fx_proc_streak` 6장이 축을 타원으로 공전. 뒤쪽은 알파를 낮추고 뒤 레이어로
  보낸다 — **회전을 파는 건 공전하는 줄기다.** 대칭인 링은 돌려도 안 보인다
- depth 를 뒤층/앞층으로 갈라 **뿌요를 감싼다**
- 색: 뿌요가 **흰 개**라 흰 회오리를 얹으면 개가 사라진다. 차가운 회색-청색

- **본체는 안 돌린다** — 회전은 spin 시트가 담고 있다

## 이동 기준 확정 (w1 지시 반영)

### "먼 쪽" — 이미 그 규칙이었다

`puyo.x < W / 2` 가 곧 **뿌요 현재 위치 기준 먼 쪽**이다.
왼쪽 끝까지 `puyo.x`, 오른쪽 끝까지 `W - puyo.x` 이므로
`puyo.x < W - puyo.x` ⟺ `puyo.x < W / 2`. 설계 문서에 "화면 중앙 기준" 이라고
써 뒀던 것이 헷갈릴 수 있어 주석을 유도식으로 고쳐 두었다.

**정확히 한가운데**(좌우 거리가 같을 때)면 **지금 걷던 방향**(`this.dir`)을 따른다.
매번 같은 쪽을 고르면 기계처럼 보이고, 무작위면 프레임마다 흔들릴 위험이 있다.

### 화면 밖으로 나간다 (바뀐 것)

전에는 `puyoLandMargin` 만큼 화면 **안**에 착지시켰다. 안에서 멈추면 "날아간다"가
아니라 "착지한다"로 읽힌다. 바꾼 것:

- **궤적**: 포물선이 아니라 **대각선 상승** `1-(1-u)²`. 초반에 확 솟고 끝에서 눕는다.
  내려올 구간이 없다 — 화면 밖으로 나가는 연출이라 필요가 없다
- **목표**: 먼 쪽 화면 끝 + `puyoExitPad`(뿌요 크기의 1.3배) 밖
- **회수**: `x` 나 `y` 가 그 여유를 넘으면 **즉시** 끝낸다. 안 보이는 것을 계속 옮기고
  똥까지 훑는 건 낭비다 (테드 퍼짐에서 같은 이유로 조기 컷을 넣었다)
- **복귀**: `gone` 상태로 `puyoReturnMs`(700ms) 쉬었다가 **나간 쪽에서 다시 걸어
  들어온다.** 반대쪽에서 나타나면 화면 밖을 가로질렀다는 뜻이 되어 더 큰 거짓말이다.
  들어오는 동안은 좌우 클램프를 풀어 둔다 (안 그러면 가장자리에 붙어 못 들어온다)

`gone` 은 시트가 없는 유일한 상태라 타입을 `PuyoSheetState | 'gone'` 으로 갈랐다.

실측: 발동 x=278 (화면 360) → 왼쪽 278 / 오른쪽 82 → **왼쪽**으로 날아 x=-52 에서
회수, 700ms 뒤 왼쪽에서 걸어 들어와 x=242 에서 배회 중.

### 배회 · 뒤집기

태이와 같은 좌우 왕복(플레이어를 안 따라간다), 경계에서 반전, 가끔 `idle`.
뒤집기는 **진행 방향**(속도 부호)으로 판단하고 `puyoFlipDead` 데드존으로 전환점
떨림을 막는다 — 참새에서 `setFlipX(cos > 0)` 로 **있는 자리**를 보다가 절반 구간에서
뒤로 나는 그림이 나왔던 것과 같은 함정이다.

| 판정 반경 | 34px | **48px** (뻗은 발만큼 넓다) |
| 점/개 | 20 | **30** |
| 임팩트 | 착지 셰이크만 | **출발 히트스톱 40ms** + 더 센 셰이크 |

시트가 안 올라왔으면 `scene.anims.exists` 가 false 라 **조용히 보통 점프로 떨어진다.**
시트 하나 때문에 능력이 죽지 않는다.

### 시트

`puyo_kick_128x128.png` 6프레임 (768x128, 0.375MB) — 발사 → 몸 늘이기 →
**앞발을 쭉 뻗고 육구가 진행 방향을 보는 결정타** → 최대 신장 → 접기 → 착지 준비.
투명 배경으로 받았다.

### VRAM

walk 0.375 + idle 0.250 + crouch 0.188 + jump 0.188 + **kick 0.375** = **1.38MB**
(`spin` 은 여전히 로딩 제외). 하이디를 고른 판에서만 올라간다.

### 회귀 (75개)

- `[H12]` 날라차기와 보통 점프가 **둘 다 나옴** — 12번 중 2/10 (설정 30%)
- `[H13]` 날라차기가 보통 점프보다 세다 (반경·점수)

확률 자체를 검사하지 않는 이유: 난수라 판마다 흔들린다. **두 갈래가 다 나오고
날라차기가 더 세다**는 구조만 못박는다.

### 날라차기 — 원본을 "화풍만" 바꿨다 (재작업)

처음에는 "날라차기를 그려 달라"고 포즈를 말로 설명했더니 **차는 느낌이 안 났다.**
그냥 나는 개였다. 고친 방법은 **레퍼런스 자체를 변환**시키는 것이다:

> "This is a STYLE CONVERSION, not a redesign. REDRAW IMAGE 1 EXACTLY AS IT IS,
> but in IMAGE 2's pixel-art style. Trace it. Keep EACH POSE PIXEL-FOR-POSE IDENTICAL,
> especially the SAME LEG AND PAW POSITIONS."

원본 6프레임이 그대로 살아났다: 준비 → 도약 → 체공 → **앞발을 쭉 뻗고 육구가 정면,
입을 벌린 결정타** → 팔로스루 → 착지.
검수: `creative/_fx/heidi-puyo/_검수_날라차기_원본대조.png` (윗줄 원본 / 아랫줄 픽셀아트)

**좌우 방향**: 원본이 오른쪽을 보고 있어 생성물도 오른쪽을 본다. 다른 시트는 전부
왼쪽 기준이고 코드가 `setFlipX(진행 방향)` 으로 뒤집으므로, 조립할 때 한 번 뒤집어
기본 방향을 맞춘다 — `build-puyo-sheet.py --flip`.

**하네스 구멍 하나**: `[H6]`·`[H10]` 이 `state === 'jump'` 일 때만 표본을 모으고 있어서,
발동이 날라차기로 갈리면 표본이 0 이라 실패했다. `'kick'` 도 비행 상태로 보게 고쳤다.

## 벽 짚고 내려오면서 날라차기 (사람 지시 · 최신)

> "음 점프를 양옆 화면까지 날라가고 화면을 짚고 다시 내려올 때 날라차기 하는 방싣으로
> 해 줄 수 있나? 벽 짚는 스트라이트 시트 필요하면 만들고."

발동 한 번이 **네 토막**이 됐다.

| | 상태 | 길이 | 하는 일 |
|---|---|---|---|
| 예비 | `crouch` | 220ms | 그대로 |
| ① | `jump` | 560ms | **직전과 반대쪽** 화면 끝까지 (첫 발동만 먼 쪽 — 아래 참고). 목표 벽이 가까우면 **멀어질 때까지 발동을 미룬다**. 끝점이 이미 높으므로 **끝점까지 선형 + 중간 웃자람**(`puyoRiseH` 0.12)으로 그린다. 예전의 바닥 기준 포물선으로는 벽에 닿는 높이를 맞출 수가 없다 |
| ② | `wall` | 260ms | 바닥에서 화면 높이의 42%(`puyoWallH`) 지점에서 **화면을 짚고 멈춘다.** 3컷(접촉 → 웅크림 → 차기)이 여기서 돈다 |
| ③ | `kick` | 520ms | 벽을 밀고 **짚은 벽에서 화면 폭의 70%** 되는 자리까지 대각선 하강. `u²` 로 가속한다 — 차고 내려오는 동작은 끝이 빨라야 한다 |

짚는 자리는 **스프라이트 바깥 끝** 기준이다 (`wallX = W - puyoWallMargin - half`).
중심을 기준으로 잡으면 몸 절반만큼 안쪽에서 허공을 짚는다.

**`puyoKickChance` 를 없앴다.** 날라차기는 확률로 갈리는 대체 동작이 아니라
**언제나 발동의 뒷절반**이다. 두 갈래를 다 보려던 `[H12]` 도 그래서 성격이 바뀌었다 —
"둘 다 나온다"가 아니라 **"매번 네 토막을 순서대로 지난다"**(8/8)를 못박는다.
넓은 판정·높은 점수(`puyoKickHitR` 48 / `puyoKickPoints` 30)는 이제 **하강 구간**의 값이다.

### 한쪽 벽에만 붙었다 — "먼 쪽" 규칙을 접었다 (사람 지적)

> "음 이러니까 한쪽 벽에만 점프를하게되네?"

**두 규칙이 서로를 물었다.**

1. 도약은 "지금 자리에서 **먼 쪽**" 으로 간다 (예전 지시)
2. 날라차기는 **벽 반대편 끝까지** 날아가 착지한다 (이번 지시)

왼쪽 벽을 차면 오른쪽 끝(x≈312/360)에 내린다. 거기서 다시 먼 쪽을 고르면
**방금 찼던 왼쪽**이다. 그래서 영원히 왼쪽만 짚는다. 우연이 아니라 필연이다.

착지를 가운데 쪽으로 당겨도 안 풀린다 — 먼 쪽 판정은 화면 중앙을 기준으로 갈리므로,
**벽 반대편 절반에 내리는 한 다음 먼 쪽은 언제나 같은 벽**이다. 날라차기가 화면을
가로지르는 것을 포기하지 않는 이상 먼 쪽 규칙과 공존할 수 없다.

→ **번갈아 간다.** 첫 발동만 먼 쪽이고, 그다음부터는 `!lastWallRight` 다.
착지 후 걷는 방향도 `dir = wallRight ? 1 : -1` 로 바꿨다 — 착지 자리가 화면 끝
근처라 바깥쪽을 보고 서면 한 걸음 만에 가장자리에 부딪혀 방향을 뒤집는다.

`[H16]` 이 이걸 지킨다 — 한 판에서 **세 번** 발동시켜 `LRL` 이 나오는지 본다.
한 번만 보면 번갈아 가는지 알 수 없다. (하네스 구멍 하나: 재발동시킬 때 점수를
`interval * (n+1)` 로 올렸더니 **똥 보너스가 밀어 올린 재진입 가드**에 삼켜져
2·3회차가 아예 안 나갔다. `lastFireScore` 위의 첫 배수로 올라가게 고쳤다.)

### 코앞으로 폴짝 뛰게 됐다 — 발동을 미룬다 (사람 지적)

> "음 근데 이러면 벽 옆에서 벽으로 뛰는 경우가 생겨 똥을 삭제하는게 좀 없는데?"

번갈아 짚게 하니 새 구멍이 났다. 날라차기가 오른쪽 끝에 내려놓는데 다음 목표가
**오른쪽 벽**이다 — 바로 옆이라 폴짝 뛰고 끝난다. 경로가 짧으니 지나가는 똥이 없다.
똥을 쓸어내는 것이 이 능력의 본체이므로 그냥 못 넘어간다.

**점수가 차도 바로 뛰지 않는다.** `onScoreMilestone` 은 `pending` 만 세우고,
목표 벽까지 거리가 화면 폭의 `puyoMinRunW`(0.70) 이상이 되는 순간 배회 갈래에서 웅크린다.
기다리는 동안 **목표 벽 반대쪽으로 물러선다** — 가만두면 하필 목표 벽 쪽으로 걸어가다
되짚어 오느라 대기가 두 배가 된다. 물러섰다 달려가 뛰는 모양이라 도약도 무거워졌다.
대기 중에는 `idle`(멈춰 서기)도 걸리지 않는다.

요구치는 **손 닿는 범위 아래로 잘라 둔다** (`W - puyoMargin - half - 1`).
화면이 좁거나 여백이 커지면 `W * puyoMinRunW` 가 물러설 수 있는 한계를 넘어
**영영 안 뛰는** 상태가 된다.

측정: 가장 짧은 도약 168px → **221px** (화면 360). 경로의 똥 제거도 10/40 → 16/40.
`[H17]` 이 하한을 지킨다.

### 착지를 안쪽으로 당겼다 (사람 지시)

> "착지 지점도 2, 3 정도로 당길 수 있나?"

`puyoLandMargin`(가장자리에서 46px) 을 **`puyoLandW`(짚은 벽에서 화면 폭의 70%)** 로 바꿨다.
반대쪽 끝에 처박히면 다음 대기 지점까지 한참을 걸어 돌아와야 한다.

실측 (화면 360, 네 자리를 `벽1 · 2 · 3 · 벽4` 로 보면):

```
1회차 — x=180 → 72px 물러서서 x=252(3) 도약 → 왼쪽 벽(1) → 착지 x=252(3) · 대기 0.7초
2회차 — x=252 → 144px 물러서서 x=108(2) 도약 → 오른쪽 벽(4) → 착지 x=108(2) · 대기 1.4초
3회차 — x=108 → 144px 물러서서 x=252(3) 도약 → 왼쪽 벽(1) → 착지 x=252(3) · 대기 1.4초
```

착지점과 **반대쪽 도약 대기 지점**이 정확히 마주 보게 되어, 되돌아 걷는 거리가
207px → **144px** 로 줄고 주기가 시계추처럼 규칙적이 됐다. 한 발동이 여전히
화면을 두 번 쓴다 (도약 221px + 날라차기 221px).

### 벽 짚기 시트

`puyo_wall_128x128.png` 3프레임. 프롬프트는 **벽을 그리지 않았다** — "a vertical wall
that is OFF THE LEFT EDGE of the frame" 라고만 하고 접촉 → 압축 → 밀어내기 세 자세를
받았다. 벽을 그리게 하면 배경이 딸려 와서 오려낼 것이 생긴다.

**생성물에 몸 한가운데가 투명하게 뚫려 나왔다** (5,754px / 5,666px 두 덩어리, 1·3프레임).
`binary_fill_holes` 는 마스크만 채우므로 그 안의 RGB 는 검은색 그대로 남아
**몸통에 검은 얼룩**이 됐다. `build-puyo-sheet.py` 에 `fill_rgb_holes()` 를 넣어 고쳤다:

1. 구멍을 **가장 가까운 밝은(≥110) 불투명 픽셀** 색으로 메운다 —
   그냥 최근접을 쓰면 구멍을 두르고 있던 **외곽선 색**이 번져 갈색 얼룩이 된다
2. 구멍 둘레의 외곽선 고리(`HOLE_RING` 10px)도 같이 지운다 — 선이 아니라 **닫힌 고리**라
   128px 로 줄이면 통째로 검은 얼룩이 된다

## 바닥 이동을 빠르게 (사람 지시)

> "바닥에서 이동을 조금 빨리 해 줄래?"

`puyoSpeed` 105 → **150px/s**. 태이(130)보다 느리게 잡아 뒀는데, 발동마다 도약 대기
지점까지 144px 을 걸어 돌아오는 구조가 되면서 **바닥에서 굼떠 보였다.**

**걷기 fps 도 같이 올렸다** (10 → 14). 속도만 올리면 발이 바닥을 미끄러진다 —
105px/s 에 10fps 였으니 150px/s 면 대략 14fps 다.

되돌아 걷는 대기: 1.4초 → **1.0초**.
