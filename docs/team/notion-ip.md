# Notion — 게임 프로젝트 홈의 설계와 작성 규칙

Notion 은 **회사 문서**다. 읽는 사람은 대표와 앞으로 뽑을 실무진이다.
첫 화면은 **게임 프로젝트 홈**(🎮 똥피하기)이고, IP(캐릭터 설정·곡·세계관)는 그 아래 한 영역이다.
에이전트용 작업 문서(어떻게·어느 파일)는 저장소에, 작업본(제안서 v1·v2…)은 작업 폴더에 둔다 — 섞지 않는다.

> 2026-10-11 'IP 허브'에서 게임 프로젝트 홈으로 재편했다 (대표 OK).
> 홈이 캐릭터 설정 위키라서 "지금 무엇을 내보내나 · 무엇이 막혔나 · 대표가 무엇을 정하나"에 답하지 못했다.
> 조사와 진단: `~/ddong-fx-work/notion/restructure_proposal.md` (출처는 같은 폴더 `research_*.md`)

## 원칙

1. **한 항목 = 한 페이지.** 캐릭터 한 명, 곡 하나, 릴리스 하나, 결정 하나가 각자 페이지다
2. **사실은 한 곳에만.** 다른 페이지는 **관계 속성으로 연결**한다. 다시 적지 않는다
3. **주인이 갈린다.**
   - 설정(외형·성격·목소리·스토리·가사) → **Notion 이 기준**
   - 게임 데이터(ID·등급·능력 수치·에셋 경로) → **저장소가 기준** (`src/`)
   - 제작 진행 상태 → **저장소가 기준** (`production/*.yaml`). Notion 에는 요약만
   - 수치(확률·천장·점수·가격) → 게임 안 설명 · 릴리스 노트 · 기획 확정본이 기준. Notion 에는 "어디가 기준인지"만
4. **확정은 대표만.** IP 항목은 `정사`(`확정 / 초안 / 폐기`), 기능 명세는 `상태 = 대표 승인`, 결정은 `상태 = 확정`.
   에이전트가 쓴 설정은 전부 `초안`. 대표 확인 전인 결정은 `제안`
5. **Notion 엔 결정 뒤의 요약만.** 작업본은 작업 폴더에 두고, 대표가 정한 결론만 기능 명세 · 결정 로그로 옮긴다
6. **릴리스가 일을 묶는다.** 업무 · 버그 · 결정 · 라이브 일정 · 기능 명세가 모두 '어느 릴리스'에 이어진다
7. **쓰는 사람이 정해져 있다** — 아래 DB 표의 '누가 언제'. 자리만 있고 쓰는 사람이 없으면 낡는다 (재편 전 운영 층이 9/28 그대로 멈춰 있었다)
8. **최신 표시.** 살아 있는 문서(마일스톤 · 기능 명세 · 라이브 일정)는 `담당 역할` 과 `마지막 확인` 을 갖는다. 30일 넘게 확인 안 된 기획은 기획 페이지의 ⚠ 칸에 뜬다

## 작성 규칙 (실무진이 읽는다)

- 첫 줄에 결론. 제목은 발견("~가 낡았다")이 아니라 결과("~가 된다")로
- 본문에 파일 경로·커밋 해시·워크스페이스 번호(w2 등)·에이전트 이름을 쓰지 않는다.
  담당은 역할명(개발·제작·음악·세계관·운영·기획)으로. 필요하면 맨 아래 `참고` 에만
- 수치를 베끼지 않는다 — 기준 위치만 쓴다. 지나간 릴리스 본문처럼 기록 자체인 것만 예외
- 결정 로그엔 **대표에게 확인받은 내용만** 쓴다. 총괄 메모로만 보이는 것은 총괄에게 묻고 쓴다
- 저장소 내부 문제(문서 낡음·미추적 파일 등)는 Notion 에 올리지 않는다
- 홈 본문은 **부분 수정만.** 통째 교체는 자식 페이지·DB 를 휴지통으로 보낸다 (2026-09-13 사고)
- 기존 페이지는 지우지 않고 `보관` 아래로 옮긴다. 결정은 지우지 않고 `뒤집힘` 으로 두고 새 결정의 `대체한 결정` 으로 잇는다

## 구조

```
🎮 똥피하기 (홈)
├─ 📅 계획      🚩 마일스톤 · 📦 릴리스 · 🗓️ 라이브 일정 · 📰 주간 현황
├─ 📐 기획      📐 기능 명세 (기둥 문서 4장 포함)
├─ 🧑‍🎤 콘텐츠   🧑‍🎤 캐릭터 · 🎵 곡 · 🎬 콘텐츠(소설·SNS)
├─ 📖 IP·세계관  🎮 게임 · 캐릭터 페이지 틀 · 세계관 검토본 · (설정 사전·사건 연표·스토리·용어집 — 세계관 확정 뒤)
├─ 🛠 운영      📋 업무 · 🐛 버그 · ⚖️ 결정 로그
└─ 🗄️ 보관      이전 에이전트 기록 · 재편 전 운영 페이지
```

캐릭터 DB 는 게임과 IP 가 같이 쓰므로 콘텐츠에 두고 IP·세계관 페이지에서 링크한다.
영역 페이지마다 맨 아래 **'쓰는 법'** 토글이 있다 — 페이지 틀은 거기가 기준이다.

### 홈 — 지금 봐야 할 세 칸만

① 이번 주 상태 · ② 대표가 정할 것 · ③ 꼭 고칠 버그 · 바로가기.
①~③ 은 연결된 DB 보기(필터가 걸린 보기)라 손으로 고치지 않는다. 사람이 쓰는 것은 ① 주간 현황뿐이다.
릴리스 · 라이브 일정 · 결정 · 마일스톤은 홈에 다시 띄우지 않는다 — 원본이 있는 영역 페이지에서 보고, 한 주 요약은 주간 현황이 맡는다.

| 칸 | 보기 조건 |
|---|---|
| ① | 주간 현황 · 주 시작이 1주 안 |
| ② | 업무 · 대표 판단 켜짐 · 완료 아님 / 결정 로그 · 상태 = 제안 |
| ③ | 버그 · (S1·S2 또는 종류 = 보안) 이고 고침 아님 |
| 기획 페이지 ⚠ | 기능 명세 · 마지막 확인이 한 달 넘음 |

> 재편 첫판(2026-10-11)은 홈에 보기를 9개 걸었다. 원본이 영역 페이지에 다 있어 같은 표를 두 번 보여 주는 셈이었고,
> 한 화면에 DB 가 다 모여 홈이 DB 목록처럼 보였다. 같은 날 세 칸으로 줄였다.

API 로 페이지에 보기를 넣을 때는 `update_content` 로 문단을 바꾸며 `<database data-source-url="collection://…" inline="true">` 를
끼우고, 생긴 보기를 `update-view` 로 거른다. `create-view`(parent_page_id)는 페이지 맨 끝에 붙어 순서를 못 정한다.

## DB — 누가 언제 쓰나

| DB | 한 페이지 = | 상태 흐름 | 누가 · 언제 |
|---|---|---|---|
| 마일스톤 | 웹 정식 출시까지의 단계 하나 | 완료 · 진행 중 · 다음 · 나중 | 단계는 대표가 정한다. 운영이 반영하고 월 1회 `마지막 확인` |
| 릴리스 | 배포 한 번 | 계획 → 잠금 → 검증 → 배포됨 | 운영 — 계획 때 줄을 만들고(버전 미정이면 '다음 릴리스'), 배포 때 본문을 채운다 |
| 라이브 일정 | 날짜 있는 라이브 일 하나 (배너는 열 때마다 새 줄) | 구상 → 계획 → 대표 승인 → 준비 끝 → 공지됨 → 진행 중 → 끝·회고 | 기획이 초안 · 운영이 공지 줄과 회고 · 대표가 승인 |
| 주간 현황 | 한 주 | 신호등 초록·노랑·빨강 | **운영이 매주 월요일**, 총괄 보고를 모아 2분 분량 |
| 기능 명세 | 시스템·기능 하나 + 기둥 문서 4장 | 구상 → 설계 → 대표 승인 → 개발 → 출시 · 보류 | 담당 역할(주로 기획)이 **대표 승인 뒤** 요약을 올린다 |
| 업무 | 대표가 알아야 할 일 하나 | 시작 전 · 진행 중 · 막힘 · 완료 | 총괄·운영. 에이전트 세부 작업은 넣지 않는다 |
| 버그 | 버그 하나 | 접수 → 확인 중 → 고치는 중 → 고침·실기 확인 필요 → 고침 · 다시 열림 | 운영·개발. 심각도는 플레이어 영향, 우선순위는 대표 |
| 결정 로그 | 결정 하나 | 제안 · 확정 · 뒤집힘 | 총괄이 대표에게 확인한 결정을 운영이 쓴다 |
| 캐릭터 · 곡 · 콘텐츠 · 게임 | 한 명 · 한 곡 · 한 편 · 한 게임 | 정사 확정/초안/폐기 | 제작·세계관(설정) · 음악(곡) · 운영(출시 구분·배너) |

공시: 라이브 일정의 `공시 체크`(확률 · 천장 · 기간 · 변경 사전 고지)는 공지할 때 켠다.
확률·천장이 바뀌는 결정은 날짜 박힌 결정 로그 + 공지 줄이 같이 있어야 한다.

  제작 상태(기획/제작/출시) · 출시일 · **출시 구분**(기본/상시/한정/이벤트) · 정사 · 테마곡(→곡) ·
  관계 캐릭터(→캐릭터) · 등장 게임(→게임) · 첫 등장 업데이트(→릴리스) · 나온 배너(→라이브 일정) · 기능(→기능 명세)

  **목소리**(톤·음역·말버릇) / 배경 스토리 / 게임별 능력(플레이어 언어로) / 음악 방향 / 변경 이력

## 정기 일 (운영)

- **매주 월요일** — 주간 현황 한 장. 홈 ① 에 뜬다
- **대표 결정이 나면** — 결정 로그 (총괄 확인 뒤). 관련 기능 명세 · 라이브 일정 · 릴리스를 잇는다
- **배포 때** — 릴리스 줄을 `배포됨` 으로, 본문에 릴리스 노트 요약. 고친 버그를 잇는다
- **월 1회** — 마일스톤 · 기능 명세 · 라이브 일정의 `마지막 확인`

## 하지 않는 것 / 나중

- **지표 DB** — 홈에서 뺐다 (2026-10-11 대표). 데이터 경로가 정해지면 가입 수 · 판수 · 뽑기 횟수부터 만든다
- **공지 DB 따로** — 지금은 라이브 일정의 '공지' 종류 줄로 충분하다
- **저장소 → Notion 자동 동기화** — 하지 않는다. 대신 수치를 베끼지 않는다
- 사업·법무 전용 공간 — 계약·매출을 다루기 시작하면 연다
