## 1. 왜 지금 것이 실패했는가

사람의 판정은 "매우 마음에 들지 않는다"였고, 실패 방향을 정확히 두 단어로 짚었다 —
**얇은 체크 타일**, **평범한 금색 원**. 현재 스크립트를 읽으면 그 두 가지가 나올 수밖에 없다.

| 증상 | 코드상의 원인 |
|---|---|
| 타일이 얇은 종이처럼 보인다 | `build_tiles()` 가 만드는 것은 **두께 없는 사각형 4점**이다. 베벨도, 측면도, 접촉 그림자도 없다. 정육면체가 아니라 정육면체 모양으로 배열된 색종이다 |
| 큐브가 입체로 안 읽힌다 | 음영이 `shade()` 한 줄 — `0.62 + 0.38·nz` 의 면 단위 평면 채색이다. AO 도 그림자도 반사도 없어서 인접한 두 면의 밝기 차만 남는다 |
| 충전이 "금색 원"으로 보인다 | `radial()` 이 그리는 건 말 그대로 **중심에서 떨어지는 감쇠 원**이다. 빛이 어디서 새어 나오는지가 없다 — 틈이 실제로 비어 있지 않으니 샐 곳이 없다 |
| 폭발이 가볍다 | 조각이 등속에 가깝게 밖으로 날고 모션 블러가 없다. `T_BURST` 가 12프레임(500ms)이나 되는데 그 안에서 "짧고 강한" 순간이 없다 |
| 프레임이 잘게 떤다 | `rng = random.Random(1000 + i)` — 프레임마다 난수 시드가 달라 잔떨림이 시간 방향으로 연속되지 않는다. 흔들림이 아니라 노이즈다 |

**보정으로 될 일이 아닌 이유**: 위 다섯 중 넷은 "2D 로 그렸다"의 직접 결과다.
틈에서 빛이 새려면 틈이 실제로 있어야 하고, 조각이 두꺼워 보이려면 측면이 그려져야 하며,
접촉 그림자는 광원과 기하가 있어야 나온다. Pillow 로 이걸 다 흉내 내는 것은
셰이딩 엔진을 새로 쓰는 일이다. **3D 렌더러를 쓰는 게 더 싸고 더 정확하다.**

## 2. 제작 파이프라인

### 2.1 도구 판단

| 후보 | 판단 | 근거 |
|---|---|---|
| 현행 Pillow 절차 생성 | ✗ | §1. 기하는 맞지만 **재질·빛·그림자가 없다**. 이 연출의 실패는 전부 그쪽에서 났다 |
| 생성 모델 (ComfyUI / GPT Image) | ✗ | 40프레임 강체다. 프레임마다 다시 그리면 면 개수와 체크 위치가 흔들려 재생 시 깜빡인다. `make-cube-sheet.py` 의 기존 판단이 옳고, 그건 그대로 유효하다 |
| After Effects | ✗ | 설치돼 있지 않고 유료다. 헤드리스 재현(`aerender`)이 되긴 하나 프로젝트 파일이 바이너리라 **스크립트로 재생성한다**는 이 저장소 원칙과 맞지 않는다 |
| three.js + headless-gl (node) | △ | 무료·스크립트지만 Windows 에서 `headless-gl` 빌드가 까다롭고(추정), 그림자·AO·모션블러를 직접 구현해야 한다. Blender 대비 이점이 없다 |
| **Blender 4.5 LTS (EEVEE Next, 헤드리스)** | **✓** | 무료, `.py` 한 파일로 씬 구성부터 렌더까지 완결, 알파 PNG 시퀀스 출력이 표준, 베벨·AO·소프트 섀도·모션블러·볼류메트릭이 전부 내장. 이 기계에 RTX 3070 이 있어 EEVEE 는 프레임당 1초 이하(추정) |

**결론: Blender.** 이 연출에 필요한 것(두꺼운 조각, 틈에서 새는 빛, 접촉 그림자, 폭발 모션블러)이
전부 Blender 의 기본 기능이고, 그중 무엇도 Pillow 에는 없다.

### 2.2 설치 (아직 하지 마라 — 승인 후)

```powershell
winget install --id BlenderFoundation.Blender --version 4.5  # LTS
# 또는 https://www.blender.org/download/lts/ 에서 4.5 LTS MSI
blender --version   # 4.5.x 확인
```

- **`pip install bpy` 는 쓰지 않는다.** bpy 휠은 Python 버전이 정확히 맞아야 하고
  (Blender 4.5 → CPython 3.11, **추정**), 이 기계의 파이썬은 3.10.6 과 3.12.11 이라 둘 다 안 맞는다.
  앱으로 깔고 **번들 파이썬**을 쓰면 버전 문제가 아예 없다.
- 추가 파이썬 패키지는 필요 없다. 시트 합치기만 Pillow + numpy 를 쓰는데,
  그건 이미 `C:\ComfyUI\.venv` 에 있다 (`make-cube-sheet.py` 와 동일).

```
build/cube/          # 중간 산출물 (.gitignore). 프레임 PNG 수백 장
```

### 2.4 재현 절차 (한 번에 붙여 넣을 수 있어야 한다)

```powershell
# 1) 프레임 렌더 — 세 패스. 각각 독립이라 순서는 상관없다
blender -b -P scripts/cube/render.py -- --pass body  --phase forge --out build/cube/forge_body
blender -b -P scripts/cube/render.py -- --pass core  --phase forge --out build/cube/forge_core
blender -b -P scripts/cube/render.py -- --pass body  --phase blast --out build/cube/blast_body

# 2) 격자 시트로 합치기 (파일명의 _WxH 는 pack-sheet.py 가 붙인다)
$PY = "C:\ComfyUI\.venv\Scripts\python.exe"
& $PY scripts/cube/pack-sheet.py --in build/cube/forge_body --cols 6 --frame 192x192 --name cubeforge
& $PY scripts/cube/pack-sheet.py --in build/cube/forge_core --cols 6 --frame 128x128 --name cubecore
& $PY scripts/cube/pack-sheet.py --in build/cube/blast_body --cols 6 --frame 256x256 --name cubeblast

# 3) 검증
& $PY scripts/cube/pack-sheet.py --verify public/assets/fx/sheets/cubeforge_192x192.png
.\scripts\verify.ps1
```

`render.py` 는 인자 없이 돌려도 항상 같은 결과가 나와야 한다 —
난수는 고정 시드 하나에서만 나오고(§2.6), 프레임 범위·해상도는 `timeline.py` 에서만 온다.

### 2.5 렌더 설정 (여기서 어긋나면 다시 렌더해야 한다)

| 항목 | 값 | 이유 |
|---|---|---|
| 엔진 | EEVEE Next | Cycles 는 같은 그림을 30배 느리게 준다. 이 연출에 굴절·코스틱이 없다 |
| Film > Transparent | **ON** | 알파 없으면 시트로 못 쓴다 |
| View Transform | **Standard** | 기본값 AgX 는 금색을 탈색시키고 섬광의 하이라이트를 눌러 버린다. VFX 시트는 톤매핑하지 않은 그림이어야 게임 안에서 예상대로 보인다 |
| 렌더 해상도 | 최종 프레임의 **3배** (576 / 384 / 768) | 축소가 곧 안티에일리어싱이다. 현행 `SS = 3` 과 같은 이유 |
| Sampling | 렌더 64 샘플 | EEVEE Next 기준. 조각 모서리와 소프트 섀도가 이 아래에서 지글거린다 |
| Shadows / AO | ON (AO distance 0.4) | **조각이 두꺼워 보이게 만드는 게 대부분 접촉 그림자다** |
| Motion Blur | `blast` 패스만 ON (shutter 0.5) | 모임·충전에 걸면 타일이 뭉개져 체크가 사라진다 |
| Bloom | **OFF** | 게임 쪽에 postFX 블룸이 따로 있다. 시트에 구우면 두 번 걸리고, 블룸을 끈 저사양 기기와 그림이 달라진다 |
| 출력 | PNG, RGBA, 8bit | |
| 카메라 | 85mm, 거리 8, 고정 | 광각으로 당기면 큐브가 왜곡돼 "3×3 면"이 안 읽힌다. 현행 `PERSP = 7.0` 이 그 실수다 |

### 2.6 씬 구성 (`render.py` 가 만드는 것)

- **조각 54개** — 6면 × 3×3. 한 칸은 한 변 0.62 의 큐브에 **베벨 0.05 / 2세그먼트**,
  칸 사이 틈 0.06. 두께가 있어야 측면이 보이고, 측면이 보여야 종이가 아니다.
- **내부 코어** — 조각 껍질 안에 한 변 1.7 의 발광체. Emission 금색(`#FFB03A`),
  강도를 키프레임으로 0 → 18 까지 올린다. **틈으로 새는 빛이 균열광이다** — 그리는 게 아니라 새는 것이다.
- **재질** — 아이보리(roughness 0.35, 약한 clearcoat) / 흑(roughness 0.25).
  체크는 재질 두 종을 번갈아 배정한다. 텍스처 없음 — 해상도에 안 묶인다.
- **조명** — 키(위 45°, 강), 림(뒤 아래, 차가운 청색, 실루엣 분리용), 필(약).
  림 라이트가 있어야 어두운 배경에서 검은 칸이 배경과 붙지 않는다.
- **난수** — `random.Random(7)` 하나. 조각의 시작 위치·지연·폭발 방향만 여기서 나온다.
  **프레임 인덱스를 시드에 섞지 않는다** (현행 `Random(1000 + i)` 가 노이즈의 원인이다).
  잔떨림은 난수가 아니라 **주파수가 올라가는 사인 합**으로 만든다 — 시간 방향으로 연속돼야 떨림으로 읽힌다.
- **패스 분리** — `--pass core` 는 껍질 조각을 홀드아웃 처리하고 코어 발광만 렌더한다.
  이게 §3 의 가산 레이어가 된다.

## 3. 레이어 분리

원칙 두 가지:

1. **기하에 붙어 있는 것만 굽는다.** 조각·균열광·파편은 큐브의 3D 자세를 따라가므로 구워야 한다.
   충격파·불똥·연기·섬광은 자세와 무관하니 코드로 얹는 게 싸고, 수치를 바꿀 때 다시 렌더할 필요가 없다.
2. **블렌드는 목적에 맞춘다** (`vfx.ts` 의 `FxBlend` 주석, 8차 교훈).
   `background2` 평균 밝기가 192/255 다. 옅은 알파로 오래 남는 것에 가산을 쓰면 밝은 배경에서 사라진다.
   → **오래 남는 것은 `normal`, 한순간 터지는 것만 `add`.**

| # | 레이어 | 출처 | 블렌드 | depth | 비고 |
|---|---|---|---|---|---|
| 1 | 흡수 궤적 | **코드** — 꽂힌 말 스프라이트 + `fx_proc_streak` 바람선 | `normal` | 5–8 (`CHESS_DEPTH` 대역) | 말이 꽂힌 자리는 매번 다르다. 구울 수 없다 |
| 2 | 파편 조각 (모임 단계) | **코드** — `fx_proc_shard`, 아이보리/흑 착색 | `normal` | 209 | 말 → 큐브 칸의 전환(§6.3). 28장, 수명 100ms |
| 3 | **본체 + 내부광(균열)** | **구움** `cubeForge` / `cubeBlast` | `normal` | 210 | 균열광은 코어 발광이 틈으로 샌 결과라 본체와 같은 패스에 이미 들어 있다 |
| 4 | 균열 코어 (가산 보강) | **구움** `cubeCore` (절반 해상도) | `add` | 212 | 여우불의 `foxFire`+`foxFireCore` 와 같은 구조. **블룸이 꺼진 기기에서도 3번만으로 그림이 성립해야 한다** — 4번은 있으면 좋은 층이지 필수가 아니다 |
| 5 | 결합 섬광 | **코드** — 화면 채우는 흰 사각 (`Graphics` 1장) | `normal`, alpha 0.30 → 0, 120ms | 320 | 가산으로 하면 밝은 배경에서 아무 일도 안 일어난 것처럼 보인다. 한 프레임 컷 역할이라 불투명이 맞다 |
| 6 | 충격파 | **코드** — `fx_proc_ring`, scale 0.25 → 3.0 / 220ms | `add` | 214 | 짧고 강해서 가산이 맞는 유일한 경우 |
| 7 | 불똥 | **코드** — `burst(scene, x, y, 'ember')` | 프리셋 기본 (`add`) | 213 | |
| 8 | 연기·먼지 | **코드** — `burst(scene, x, y, 'smoke')` | `normal` | 208 (본체 **뒤**) | 앞에 깔면 폭발을 가린다. 뒤에서 퍼져야 부피가 생긴다 |

`playFx` 는 `PlayFxOptions.depth` 로 레이어별 depth 를 다 받을 수 있고,
`blend` 오버라이드도 이미 열려 있다 (8차 작업). **vfx.ts 에 새 API 는 필요 없다** —
단 하나, §6.4 의 시트 이어붙이기만 호출부(TedAbility)에서 처리한다.

블룸: 4·6·7번이 `add` 라 `attachBloom` 대상이 된다. `BLOOM_LAYER_DEPTH = 122` 이므로
**depth 212 이상에 얹는 레이어는 블룸 레이어에 담기지 않는다.** 이건 의도한 것이다 —
큐브는 이미 구워진 그림에 빛이 들어 있고, 여기에 화면 블룸까지 겹치면 흰 덩어리가 된다.
불똥(213)만 블룸을 받게 하려면 depth 를 121 로 내려야 하는데, 그러면 똥(100) 위·플레이어 아래가
섞여 정리가 안 된다. **결론: 이 연출은 블룸에 기대지 않는다.** (저사양 스위치가 꺼져도 같은 그림)

## 4. 프레임 타임라인

30fps. 프레임 수를 늘려서가 아니라 **박자**로 만든다 — 멈칫 → 압축 → 짧고 강한 파열 → 긴 잔광.

### 4.1 `cubeForge` — 36프레임 / 1200ms / 192×192

| 프레임 | 시각(ms) | 구간 | 무슨 일이 일어나는가 |
|---|---|---|---|
| 0–7 | 0–266 | 접근 | **큐브는 아직 없다.** 중심에 아주 옅은 아지랑이와 먼지만. 이 구간의 주인공은 코드가 움직이는 진짜 체스 말이다 |

### 4.4 열려 있는 판단 — 총 길이 2.0초

큐브가 플레이어 몸 중앙에 2초 동안 떠 있다. 그 사이에도 똥은 떨어지고 플레이어는 피해야 한다.
**가릴 위험이 실재한다.** 두 가지 안전장치를 설계에 넣었다:

- 충전 구간 본체 알파 0.88, 불투명 코어의 화면 지름을 **90px 이하**로 묶는다
  (플레이어 표시 크기가 50×80 이라 머리와 발이 비어져 나온다)
- 그래도 길다고 판단되면 **충전 400 → 300ms** 로 줄여 총 1.8초. 이때 `cubeForge` 는 33프레임이 된다

어느 쪽으로 갈지는 실기에서 사람이 보고 정하는 게 맞다. 설계는 2.0초 기준으로 쓰되
이 수치만 `timeline.py` 한 곳에서 바뀌게 해 둔다.

## 6. TedAbility 연결

확인된 결함 3건을 전부 해결안에 넣었다. **아래는 설계다. 코드는 승인 후에 쓴다.**

### 6.1 결함 1 — 말의 목적지가 발동 시점에 고정된다

현재 `clearBoard()` 는 `player.x/y` 를 읽어 트윈의 종점으로 박는다.
반면 `onUpdate()` 는 큐브를 매 프레임 `player.x/y` 로 따라 붙인다.
**이동 중 발동하면 말은 과거의 자리로, 큐브는 지금의 자리로 간다.**
`chessSuckMs = 520ms` 동안 플레이어가 최고 속도로 달리면 300px 넘게 벌어진다.

**고침: 트윈을 버리고 `onUpdate` 안에서 매 프레임 보간한다.**

```
// 말마다: { obj, sx, sy, t0, delayMs, durMs }
onUpdate:
  p = clamp((now - t0 - delayMs) / durMs, 0, 1)
  k = easeIn(p)                       // Quad.easeIn — 지금 트윈과 같은 감각
  obj.setPosition(lerp(sx, player.x, k), lerp(sy, player.y, k))
  obj.setScale(...), obj.setAlpha(...)  // 같은 p 에서 파생
  if (p >= 1) shatter(obj)            // §6.3
```

7개뿐이라 매 프레임 비용은 무시할 수 있다. 부수 효과로 **플레이어가 움직이면
말의 궤적이 자연스럽게 휜다** — 목표가 움직이니 직선이 곡선이 된다. 이게 오히려 맞다.
`scene.tweens` 를 안 쓰므로 `onDestroy` 에서 `killTweensOf` 를 할 것도 줄어든다.

### 6.2 결함 2 — 도착 790ms, 결합 섬광 583ms

```
현행 계산:  chessSuckMs 520 + chessFadeStep 45 × (chessStackMax 7 − 1) = 790ms
현행 시트:  T_LOCK 시작 14프레임 ÷ 24fps                              = 583ms
            → 결합이 207ms 먼저 끝나고, 그 뒤에 말이 도착한다
```

**고침: 두 숫자를 같은 상수에서 파생시키고, 지연이 있어도 도착은 한 시점에 모은다.**

```
시트 계약 (cube-timeline.json 이 내보낸다)
  CUBE_GATHER_MS = 600        // 결합 섬광 프레임 18 ÷ 30fps
코드
  PIECE_ARRIVE_MS = 500       // 말은 섬광보다 100ms 먼저 도착해 파편이 될 시간을 번다
  SHARD_MS        = 100       // 500 → 600. 섬광이 파편을 덮으며 큐브로 바뀐다
  delay_i = i × 28            // 0 ~ 168ms, 계단식 출발은 유지한다
  dur_i   = PIECE_ARRIVE_MS − delay_i     // ★ 늦게 떠난 말은 짧게 간다 → 전부 500ms 에 도착
```

핵심은 `dur_i = ARRIVE − delay_i` 다. 지금은 `duration` 이 모두 같고 `delay` 만 달라서
**늦게 출발한 말이 늦게 도착한다**. 출발을 어긋뜨리는 이유(동시에 움직이면 리셋처럼 보인다)는
그대로 살리면서, 도착만 한 점에 모은다.

`chessStackMax` 가 바뀌어도 `delay_max = (max−1)×28 < ARRIVE` 만 지키면 성립한다.
`abilityParams.ts` 에 주석으로 이 부등식을 박아 두고, 하네스에서 검사한다(§7).

### 6.3 결함 3 — 말 7개가 어떻게 3×3 면이 되는가

지금은 전환이 없다. 말이 줄어들며 알파 0.15 로 사라지고, 별개로 시트의 조각이 나타난다.
**다른 물건 두 개가 교대할 뿐이라 "말이 큐브가 됐다"가 성립하지 않는다.**

**고침: 말 하나가 조각 넷으로 부서진다.**

```
말 7개 × 조각 4장 = 28조각   ≈   큐브 한 자세에서 보이는 칸 수 3면 × 9칸 = 27칸
```

숫자가 맞는 게 우연이 아니다. `chessStackMax = 7` 이 이 연출의 근거다.

- `t = 500ms` 에 각 말이 중심에 닿는 순간, 그 자리에서 **`fx_proc_shard` 4장**을 뿌린다.
  아이보리/흑을 번갈아 착색한다 — 체크무늬의 예고다
- 조각은 중심에서 반지름 ~55px 까지 살짝 벌어졌다가(0–40ms), 안쪽으로 빨려 들어가며
  스케일 0 으로 수축한다(40–100ms)
- `t = 600ms` **결합 섬광이 이 순간을 덮는다.** 조각이 큐브의 어느 칸에 정확히 들어맞을
  필요는 없다 — 섬광이 컷이고, 컷 뒤에는 완성된 큐브가 있다. 이건 편법이 아니라
  프레임 시트와 코드 스프라이트를 잇는 정석이다 (구운 큐브의 3D 원근과 코드가 그린 2D 좌표는
  원리상 정확히 맞출 수 없다)
- 왜 말 스프라이트를 줄여서 쓰지 않는가: 작아진 체스 말은 여전히 **체스 말로 읽힌다**.
  큐브 칸으로 읽히려면 모서리가 각진 사각 조각이어야 한다. 새 에셋은 필요 없다 —
  `fx_proc_shard` 가 이미 흰색이라 자유롭게 착색된다

시트 쪽도 맞춰 굽는다: `cubeForge` 8–17프레임의 조각은 **중심 반경 55px 부근에서 출발**한다.
코드의 파편이 사라지는 반경과 같다. 두 그림이 같은 껍질에서 만나야 이어진 것으로 읽힌다.

### 6.4 두 시트 이어붙이기

`playFx` 는 애니메이션이 끝나면 스프라이트를 파기한다. 이음새 처리:

```
clearBoard():
  if (this.cubeStage) return           // 겹치면 버린다
  this.cubeStage = 'forge'
  this.cube = playFx(scene, 'cubeForge', px, py, {
      scale, depth: 210,
      onComplete: () => this.startBlast(api),
  })
  this.core = playFx(scene, 'cubeCore', ...)   // forge 12프레임 시점에 맞춰 지연 시작
  ... 말 보간 시작 (§6.1)

startBlast(api):
  if (this.cancelled) return           // onDestroy 에서 세운다
  if (!api.scene.scene.isActive()) return
  this.cubeStage = 'blast'
  impact(scene, { hitstop: 70, shake: { duration: 260, intensity: 0.006 } })
  this.cube = playFx(scene, 'cubeBlast', player.x, player.y, {
      scale, depth: 210, onComplete: () => { this.cubeStage = null; this.cube = null },
  })
  flash(scene) · shockwave(scene) · burst('ember') · burst('smoke')

onUpdate(api):
  this.cube?.setPosition(player.x, player.y)   // 두 단계 모두 몸을 따라간다
  this.core?.setPosition(player.x, player.y)
```

- `onComplete` 는 **강제 파기(`clearSceneFx`)에서도 불린다.** `cancelled` 플래그와
  `scene.isActive()` 를 둘 다 확인해야 씬이 내려간 뒤 폭발이 터지지 않는다
- `cubeBlast` 0프레임이 `cubeForge` 35프레임의 복제라 한 프레임 공백이 생겨도 안 보인다
- 폭발은 **그 순간의 플레이어 좌표**에서 시작한다. 충전 내내 몸을 따라왔으니 자연스럽게 이어진다
- 히트스톱 70ms: `Clock.now` 는 `timeScale` 의 영향을 받지 않으므로 GameScene 의 rAF 비율
  안티치트(5초 창, 0.70–1.30)에 잡히지 않는다. `physics.world` 를 **일시정지하지 않는다**
  (안티치트 4계층이 `isPaused` 를 본다). `vfx.ts` 의 `HITSTOP_MAX_MS = 200` 안이다

# 10. 픽셀 판본 (2026-09-12, 채택)

사람이 `creative/_fx/ted-cube/pixel-chatgpt/` 의 픽셀아트 4장을 최종 아트 디렉션으로 채택했다.
**게임 기본 재생을 픽셀 판본으로 바꾸고, 3D 판본은 전부 보존한다.**

## 10.1 전환 지점 — 한 줄

```ts
// src/utils/vfx.ts
export const CUBE_VARIANT: CubeVariant = 'pixel';   // 'render' 로 바꾸면 3D 판본으로 복구
```

`CUBE_SHEETS` 가 이 값에서 파생되고, 시트 키·가산 발광층 유무·**코드가 얹는 부드러운 레이어**
(발광 링·충격파·불똥·연기)까지 한꺼번에 갈린다. `TedAbility` 는 키를 직접 쓰지 않고 여기만 본다.
§9 에서 넣은 `FX_SHEET_GROUPS` 도 여기서 파생되므로 `character.ts` 는 여전히 손대지 않는다.

## 10.2 그리는 방법 — 3D 를 줄인 게 아니다

`scripts/cube/pixel.py` 가 **최종 프레임 크기(192 / 256)에서 직접** 그린다.
안티에일리어싱 없는 폴리곤 채우기라 모든 모서리가 픽셀 격자에 떨어진다.
Blender 는 쓰지 않는다.

**네이티브를 192 로 잡은 근거 (실측)**

| 기준 | 크기 | 정수배 확대? | 픽셀 덩어리 |
|---|---|---|---|
| `public/assets/fx/sheets/chess_96x128.png` | 96×128/프레임 | 아니오 (1:1) | 1px |
| `public/assets/players/ted_front.webp` | 212×312 | 아니오 (1:1) | 1px |
| 채택 기준 이미지 | 1254px | — | ≈8px → 네이티브 ≈157px |

저장소의 픽셀 기준 두 개가 네이티브 1:1 · 1px 외곽선이고, 채택 이미지의 네이티브 해상도도
우리 프레임(192)과 같은 자리수다. 96 에 그려 ×2 로 키우면 픽셀이 체스 말보다 **두 배 거칠어져**
나란히 놓았을 때 따로 논다. 그래서 "저해상도 → 정수배 확대"의 **취지(줄이지 않는다)** 는 지키되
네이티브를 192 로 잡았다 — 이건 지시와 다른 판단이므로 §10.6 에 적어 둔다.

**아이소메트릭 2:1 격자.** 가로 2px 갈 때 세로 1px 내려간다. 임의 각도 회전은 쓰지 않는다
(채택 4장도 전부 같은 각이다). 충전감은 회전이 아니라 **이음새 밝기 단계 · 정수 px 압축 ·
각진 광선**으로 만든다.

**이음새 만드는 법.** 칸마다 ① 검은 껍질(격자 0.56) ② 금색 껍질(0.50) ③ 칸 본체(0.38)를
차례로 겹친다. 큰 심지 하나만 두면 틈(2px)이 양쪽 외곽선(1px+1px)에 다 먹혀 이음새가
아예 안 보인다 — 실제로 첫 시도가 그랬다.

# 11. 원화 판본 — 준비 (2026-09-12)

§10 의 픽셀 판본은 **채택 원화에서 팔레트만 뽑고 형태는 코드로 새로 그린 것**이었다.
요구는 그게 아니라 **ChatGPT 가 그린 그림 자체가 게임에 들어가는 것**이다. 정정한다.
절차 픽셀판(`cubepx*` + `pixel.py`)은 비교용으로 보존하고 기본에서 내린다.

composer(w8)의 중간 키프레임이 오기 전에 **실측 · 검증 도구 · 조립 파이프라인**을 먼저 만들었다.

## 11.1 원화 실측 (composer 에게 줄 근거)

| 파일 | 캔버스 | 알파 | 큐브 실루엣 | 큐브 중심 (캔버스 중심 대비) |
|---|---|---|---|---|
| `01_gather` | 1254×1254 RGB | **없음** | (단일 큐브 없음) | — |
| `02_assemble` | 1254×1254 RGB | **없음** | **464×512** | (+7, −1) |
| `03_charge` | 1254×1254 RGB | **없음** | ~587×550 (발광 포함) | **(−21, −40)** |
| `04_burst` | 1254×1254 RGB | **없음** | (단일 큐브 없음) | — |

**두 가지가 바로 문제로 잡힌다.**

1. 네 장 모두 **알파가 없다** — 배경이 칠해져 있다. 배경 제거가 필요하다
2. `02` 와 `03` 의 큐브 중심이 **약 40px 어긋나 있다.** 이대로 이어 붙이면 충전에
   들어가는 순간 큐브가 튄다. composer 가 맞춰 줘야 하는 것이 바로 이 정렬이다

원화의 픽셀 덩어리는 1254px 기준 약 8px → 네이티브 해상도 약 157px.

## 11.2 전달 규격 — `creative/_fx/ted-cube/ALIGNMENT.md`

`scripts/cube/artwork.py spec` 이 생성한다. 요지:

- 캔버스 **1024×1024 RGBA**, 배경 알파 0 (= 게임 blast 프레임 256 × **4**)
- 원화를 **확대·축소하지 마라.** 캔버스에 놓을 때 정수 px 평행이동만
- 큐브 실루엣 **464×512 ±16**, 중심은 **캔버스 정중앙 ±4**, 각도는 `02` 로 통일
- forge 구간은 가운데 **768×768** 만 살아남는다 (게임 프레임 192 × 4)
- 형태가 바뀌는 순간마다 키프레임이 필요하다 (받는 쪽은 홀드·평행이동밖에 못 한다)

**축소 배율 4의 근거**: `02` 의 큐브가 464px 이고 게임에서 약 120px 이어야 하므로
464/120 ≈ 3.9 → 정수 4. 원화는 **한 번도 확대되지 않고 딱 한 번 정수배로** 줄어든다.

## 11.3 조립 파이프라인 — `scripts/cube/artwork.py build`

원화 픽셀을 보존하는 네 가지만 쓴다. 그림은 그리지 않는다.

1. **홀드** (같은 그림 유지) 2. **정수 px 평행이동** 3. **정수 자르기** 4. **정수배 축소**

배치는 `scripts/cube/keyframe-map.json` 에 표로 둔다 — 코드를 고치지 않고 구간을 바꾼다.
회전은 하지 않는다. 각도가 필요하면 **그 각도의 키프레임을 composer 에게 요청**한다.

## 12.2 배율 정규화 — composer 가 알려온 문제의 해법

composer 의 `metrics.md` 가 짚은 그대로 **원화마다 큐브가 그려진 크기가 다르다**

대신 **키프레임마다 정수 축소 배율을 다르게** 골랐다. 배율은 두 가지를 동시에 정한다 —
(1) 화면에서의 큐브 크기 (2) 원화를 얼마나 넓게 보는가(창 = 프레임px × 배율).
그래서 **창 ≥ 원화 내용 bbox** 도 같이 만족해야 프레임 경계에서 잘리지 않는다.

| 키프레임 | 큐브 원본 | 배율 | 화면 큐브 | 창 ≥ 내용 bbox |
|---|---|---|---|---|
| 01_gather | — | ÷7 | — | 1344 ≥ 1254 ✓ |
| 01b_clump | — | ÷6 | — | 1152 ≥ 875 ✓ |
| 02_assemble | 464px | ÷4 | **116** | 768 ≥ 694 ✓ |
| 02b_firstlight | 464px | ÷4 | **116** | 768 ≥ 539 ✓ |
| 03_charge | 603px | ÷6 | **100** | 1152 ≥ 1092 ✓ |
| 03b_maxcompress | 480px | ÷5 | **96** | 960 ≥ 565 ✓ |
| 04_burst / 05_afterglow | — | ÷5 | — | 1280 ≥ 1254 ✓ |

116 → 116 → 100 → 96 — **압축 아크가 배율 선택에서 그대로 나온다.**
÷4 로 통일했다면 충전에서 큐브가 30% 커졌을 것이다.

  직선 자국을 남기고, 픽셀아트라 알파로 흐릴 수도 없다. 다만 원화의 광선이 조각들을 하나로
  이어 놓아 **성분 하나가 화면의 80% 를 차지하는 경우**가 있어서, 면적 20% 를 넘는
  주요 덩어리는 버리지도 움직이지도 않는다 (버리면 그림이 통째로 날아간다)
- **`speed`** — 잔해 성분만 방사 방향으로 민다. 이동량은 **축소 배율의 배수**여야 한다.
  아니면 NEAREST 가 집는 픽셀 위상이 바뀌어 같은 조각이 프레임마다 다르게 뭉개진다

# 13. 파열 파동 + 일반 똥 일괄 제거 (2026-09-12)

## 13.1 파동 — 반투명 에너지 띠, **절차 생성**

처음엔 흑백 각진 픽셀 링을 시트로 구웠는데, 사람이 방향을 바꿨다 — **부드러운 반투명 띠**다.
저장소의 이펙트는 원래 부드러운 애니풍 2D 다 (`lotus`·`foxfire`·`kbeam` 의 반투명 픽셀이
14~43%, 캐릭터·체스 말은 1~2%). 발광은 원래 부드럽게 쌓는다.

**시트가 아니라 절차 생성이다.** `FX_REGISTRY.cubeWave` 에 `draw` 함수를 달아
첫 재생 때 캔버스에 그려 텍스처 한 장(160×160 × 9프레임 = 0.88MB)을 만든다.
다운로드 0, 파일 0. 시트로 구울 이유가 없다 — 링은 수식으로 나오고, 부드러운 그림이라
배율을 올려도 깨지지 않는다.

**기존 `shockwave` 키는 건드리지 않았다.** 구미·K·무기가 쓰고 있어서 새 키를 따로 팠다.

### 한 겹의 단면


밝은 배경(`background2` 평균 192/255)에서 가산 흰색은 사라지고, 어두운 배경에서는
검정이 사라진다. **둘을 한 띠 안에 같이 둬서** 밝은 데선 테두리가, 어두운 데선 코어가
형태를 잡는다. 반투명이라 배경이 비쳐 보인다.

## 13.2 일반 똥 일괄 제거

파열 순간 `TedAbility.clearNormalPoops()` 가 `api.poops` 를 훑어 **`recycle(true)`** 한다.

  여기서 건드릴 수 없다 (`smashPoops` 가 같은 그룹만 치는 이유와 같다)

사라지는 연출은 파동 하나가 맡는다.

## 14.6 하네스에서 드러난 것 — `scene.time.now` 가 없었다

파동 겹이 하네스에서 하나도 안 뜨길래 파고들었더니 **스텁에 `scene.time.now` 가 없었다.**

모든 시간 계산이 **NaN** 이 되고, `t >= cue.at` 같은 비교가 조용히 false 가 된다.

그 탓에 **연출 큐(코어·결합 섬광·충전 링·파동)가 한 번도 실행되지 않고 있었고**,
말 흡수는 `u < 1` 이 NaN 비교로 false 가 되어 **첫 틱에 전부 도착한 것으로 처리**됐다.
지난 보고의 "도착 편차 0ms / 오차 0px" 이 그래서 나온 값이었다 — 설계가 맞아서가 아니라
비교가 전부 건너뛰어져서다.

`now` 를 넣고 다시 재니 **도착 편차 0ms, 도착 좌표 오차 0~6px** 이다.
(6px 은 16ms 틱 동안 420px/s 로 움직인 거리 6.7px — 계측 해상도지 설계 오차가 아니다.
합격선 20px.) 결론은 같지만 **이번 값은 실제로 코드가 돈 결과다.**

같이 고친 것 둘:
- `clearBoard` 가 **재생을 걸기 전에 상태(큐·흡수 목록)를 다 세운다.** `playFx` 의
  `onComplete` 가 동기로 불리면 `startBlast` 가 먼저 돌아 버리는데, 그 뒤에 큐를 덮으면
  파열 연출이 통째로 사라진다
- `startBlast` 는 큐를 **덮지 않고 덧붙여** 시각순으로 정렬한다
- `onUpdate` 는 `cubeStage` 가 비어도 **큐가 남아 있으면 계속 돈다**

## 15.1 착지 위치 — 층화 추출

이전에는 말이 떨어질 때마다 **독립 균등 난수**로 착지 x 를 뽑았다.
난수가 고르게 퍼진다는 건 착각이다 — 7~10개를 그렇게 뽑으면 근처에 몰리는 조합이
확률적으로 자주 나온다. 실측으로 **판의 100% 에서 두 말이 20px 안에 붙었다.**

**주머니 방식**: 착지 구간을 `chessStackMax` 칸으로 나누고, 칸 번호를 섞어 담은 주머니에서
하나씩 꺼내 **그 칸 안에서만** 위치를 뽑는다. 판이 비워지면(`clearBoard`) 주머니를 다시 채운다.

- 보장되는 최소 간격 = 칸너비 × (1 − `chessLandJitter`)
- 안전망으로 이미 꽂힌 말과 `chessLandMinGap` 보다 가까우면 같은 칸에서 몇 번 다시 뽑는다.
  **최소 간격이 칸보다 크면 재시도가 절대 성공 못 하므로 코드에서 칸너비의 80% 로 깎는다**
- 상한(`chessMaxAlive`)에 걸려 건너뛴 낙하는 **칸을 소비하지 않는다** (슬롯 추첨이 상한 검사
  뒤에 있다). `onDestroy` 와 `clearBoard` 에서 주머니를 비워 씬 재시작에 쏠리지 않게 한다

## 15.2 좁은 화면 판단

말 폭이 `chessHeight 72 × 0.75 = 54px` 인데, **말 10개 기준 칸너비는 30~37px** 이다.
10개를 안 겹치게 세우려면 `54 × 10 + 여백 = 600px` 이 필요하고 그런 세로 화면은 없다.
**겹침 자체는 못 없앤다.** 대신 두 가지로 다룬다.

1. 중심이 몰리는 것을 막는다 (위 표 — 이상적인 균등 배치가 칸너비 30~37px 간격이고
   층화가 그 절반을 보장한다)
2. `chessLandYDrop` (7 → **10px**) 으로 착지 높이를 조금씩 달리해 **겹친 말이 '충돌' 이
   아니라 '앞뒤' 로 읽히게** 한다

말은 **depth 5** 라 똥(100)·플레이어보다 뒤에 깔린다 — 바닥이 빽빽해져도 플레이 화면을
가리지 않는다.

# 16. 테드 점수 (2026-09-12)

| 값 | 이전 | **현재** |
|---|---|---|
| `chessPoopPoints` | 5 | **30** (낙하 경로에서 깬 똥 개당) |
| `cubeBurstPoints` | — | **100** (파열 **정액**, 지운 개수와 무관) |

## 16.1 재진입 가드가 이번 작업의 핵심이다

`addAbilityBonus` 는 GameScene 안에서 **점수를 1씩 올리며 마일스톤을 호출**한다.
낙하 간격이 40점이라 가드 없이 100점을 주면 그 자리에서 말이 2~3개 즉시 떨어지고,
그 말이 또 똥을 깨서 점수를 주는 연쇄가 생긴다.

`smashPoops` 와 **같은 순서**로 막는다 — 주기 전에 먼저 올린다.

```ts
this.lastChessScore += TED_PARAMS.cubeBurstPoints;   // 먼저
api.addAbilityBonus(TED_PARAMS.cubeBurstPoints);     // 그 다음
```

**정액으로 준 이유**: 파열은 화면의 일반 똥을 **한 번에 최대 60개** 지운다.
개당으로 주면 30 × 60 = 1800점이 한 프레임에 들어온다.

## 16.2 측정 (하네스, 실제 코드)

```
재진입 가드 — 낙하 간격 40점
  파열 정액 +100점       → 그 구간 마일스톤 2개, 실제 낙하 0개
  똥 6개 × 30점 = +180점 → 그 구간 마일스톤 4개, 실제 낙하 0개
  보너스 구간을 지난 뒤(320점) 낙하 1개 — 가드는 영구가 아니다
```

하네스의 `addAbilityBonus` 는 GameScene 과 **같은 방식**으로 점수를 1씩 올리며
마일스톤을 호출한다. 가드가 없으면 각각 2개·4개가 떨어졌을 자리다.

`chessPoopPoints` 가 6배가 되면서 `smashPoops` 의 기존 가드도 그만큼 크게 작동한다 —
K 와 같은 구조로, 발동 간격이 "스스로 번 점수" 가 아니라 **"플레이로 번 점수"** 기준이 된다.

## 16.3 같이 고친 것

  `말 10개가 쌓이면 몸 중앙으로 빨려 들어가 큐브가 되었다가 터진다 — 화면의 일반 똥 전부 제거 (+100점)`.

- **`clearNormalPoops` 의 낡은 주석** — "점수는 주지 않는다. 그래서 재진입도 없다" 는
  이제 틀렸다. 정액 보너스는 `startBlast` 가 가드와 함께 준다고 고쳤다

# 17. 화면 중앙 · 배율 분리 · 수치 (2026-09-12)

## 17.1 큐브가 서는 자리 — 화면 중앙 고정

플레이어를 따라다니지 않는다. `scene.scale` 기준 화면 좌표라 기기마다 같은 자리에 선다.

```ts
cubeCenterX: 0.5,   // 화면 폭 대비
cubeCenterY: 0.42,  // 화면 높이 대비
```

**세로를 0.42 로 잡은 근거.** 정확히 한가운데(0.5)면 플레이어의 회피 구역(`H - 80` 부근,
640 화면에서 y 520~600)과 가까워 큐브가 피할 길을 덮는다. 더 위(0.3)면 점수 HUD 와 겹친다.
0.42 는 그 사이의 빈 띠다 — 640 화면에서 y 269, 큐브 몸통(84px)이 y 227~311 을 차지한다.

같은 중심을 쓰는 것: 말 흡수 목표 · 조각(shard) · forge/blast 시트 · 코어 ·
충전 링 · **파동 4겹** · 불똥·연기. 전부 `cubeCenter(scene)` 한 곳에서 나온다.

**죽은 코드 정리.** `onUpdate` 가 매 프레임 `cube.setPosition(player.x, player.y)` 하던
두 블록을 지웠다. 이제 남은 건 회수된 참조를 null 로 되돌리는 두 줄뿐이다.

# 18. 파열을 화면 가로 꽉 차게 (2026-09-12)

생성(forge)은 0.72 그대로, **파열(blast)만** 화면 가로를 채운다.

## 18.1 배율 — 런타임 계산, 정수만

```ts
function blastScale(scene) {
  const need = (scene.scale.width * cubeBlastFillW) / cubeBlastContentPx;
  return clamp(Math.ceil(need), 1, cubeBlastScaleMax);
}
```

- **상수로 박지 않는다.** `main.ts` 가 `Phaser.Scale.RESIZE` 라 폭이 기기마다 다르다
- **기준은 프레임이 아니라 내용 폭이다.** 프레임은 256px 인데 파편이 실제로 닿는 폭은
  **250px** (24프레임 전부의 알파 bbox 실측, 여백 2%). 프레임 기준으로 맞추면 그림이 화면에 안 닿는다
- **정수만 쓴다.** 1.76 같은 소수 배율은 NEAREST 로도 어떤 픽셀이 2칸, 어떤 픽셀이 1칸이 되어
  격자가 불규칙해진다. 올림(ceil)이라 화면보다 넘치는데, 파열에서는 모자란 것보다 낫다

| 화면 폭 | 필요 배율 | **정수(ceil)** | 스프라이트 | 내용 폭 | 화면 대비 |
|---|---|---|---|---|---|
| 320 | 1.28 | **2** | 512 | 500 | 156% |
| 360 | 1.44 | **2** | 512 | 500 | 139% |
| 390 | 1.56 | **2** | 512 | 500 | 128% |
| 430 | 1.72 | **2** | 512 | 500 | 116% |
| 820 | 3.28 | **4** | 1024 | 1000 | 122% |

## 18.2 NEAREST — 이 시트에만

`main.ts` 의 `render.antialias: true` 는 전역이다. 픽셀 원화를 2~4배로 키우면서
선형 보간이 걸리면 여태 한 게 다 뭉개진다. **전역을 건드리지 않고 이 텍스처만** 바꾼다.

```ts
if (def.nearest) {
  scene.textures.get(def.textureKey)?.setFilter(Phaser.Textures.FilterMode.NEAREST);

```

`FxSheetAsset` / `FxDefinition` / `registerFxSheet` 에 `nearest?: boolean` 을 달고,
`ensureFxAnim` 이 애니메이션을 만들 때 한 번 건다.

**어디에 걸었나**: `cubeArtBlast` · `cubePxBlast` — **확대해서 쓰는 파열 시트만**.

# 19. 큐브 반투명 (2026-09-12)

**표시 알파만 건드린다.** 시트에는 알파를 굽지 않았다 — 구우면 원본 원화와 달라지고
`verify-artwork.py` 가 그걸 잡아내며, 되돌리기도 어렵다.
시트 파일 3종 전부 이번 작업에서 바이트 하나 안 바뀌었다.

## 19.1 왜 균일 알파로 충분한가 — 대비는 배경과 무관하다

걱정했던 "어두운 배경에서 검은 칸이 녹아 3×3 이 안 읽힌다" 는 **일어나지 않는다.**
균일 알파로 합성하면

```
(bg + A·(이보리 − bg)) − (bg + A·(검은칸 − bg)) = A·(이보리 − 검은칸)
```

**배경이 식에서 사라진다.** 알파는 큐브 안쪽 대비를 A배로 줄일 뿐이고, 그 값은
밝은 배경이든 어두운 배경이든 **정확히 같다**. 시트 실측(assemble 프레임):

| | 시트 안 휘도 |
|---|---|
| 아이보리 칸 | 215.5 |
| 검은 칸 | 29.8 |
| 금 이음새 | 150.8 |

| 표시 알파 | 체크 대비 | 금−아이보리 |
|---|---|---|
| 1.00 | 185.8 | 64.8 |
| 0.90 | 167.2 | 58.3 |
| **0.82** | **152.3** | **53.1** |
| 0.70 | 130.0 | 45.3 |
| 0.50 | 92.9 | 32.4 |

기준점: 게임의 **체스 말 스프라이트**가 아이보리 190 / 검정 22 → 대비 **168** 이다.
`0.82` 의 152 는 그와 같은 자리수라 3×3 판독이 기존 에셋 수준을 유지한다.

**"조각 두께가 죽는다" 도 해당 없다.** 큐브는 한 장의 평면 스프라이트라 반투명이어도
앞뒤 면이 서로 비치지 않는다. 면 사이 명암 단계는 위 식대로 비율이 그대로 보존된다.

## 19.2 고른 값

| | 알파 | 근거 |
|---|---|---|
| `cubeForgeAlpha` | **0.82** | 스프라이트 138px 로 작아 가림이 적다. 체크 대비 152 = 체스 말 수준 |
| `cubeBlastAlpha` | **0.72** | 파열 시작. 섬광 구간은 진해야 한다 |
| `cubeBlastAlphaEnd` | **0.34** | 다 퍼졌을 때. 화면 가로를 넘으므로 플레이가 비쳐야 한다 |

**대안 중 고른 것: 알파 램프.** 파열은 `0.72 → 0.34` 로 `Quad.easeIn` 트윈이다.
커질수록 옅어지니 **가리는 면적이 커지는 만큼 투명도가 상쇄**한다. 단순 고정 알파로는
시작(작고 진해야 함)과 끝(크고 옅어야 함) 중 하나를 포기해야 한다.
트윈은 `playFx` 가 스프라이트를 회수할 때 `killTweensOf` 로 같이 정리된다.

**"검은 칸만 덜 투명하게" 는 하지 않았다.** 스프라이트 하나의 알파는 균일해서
칸마다 다르게 줄 수 없다. 같은 시트를 `MULTIPLY` 블렌드로 한 번 더 깔면 어두운 칸만
더 진해지긴 하는데 — (1) §19.1 대로 균일 알파로도 대비가 이미 충분하고,
(2) 드로우콜이 2배가 되며, (3) `maxConcurrent: 1` 과 충돌해 슬롯을 더 써야 한다.
**효과 대비 값이 안 맞아 버렸다.**

# 20. 방향 전환 — 큐브를 빼고 말이 직접 퍼진다 (2026-09-12)

사람이 연출을 바꿨다. **큐브로 뭉치지도, 충전하지도, 파열하지도 않는다.**
바닥의 말 10개가 화면 한가운데로 모였다가 **그대로 사방으로 터져 나가고,
퍼지는 말이 지나간 자리의 똥만 지워진다.**

## 20.1 되살리는 방법 — 한 줄

```ts
// src/utils/vfx.ts

```

`FX_SHEET_GROUPS.cubeBurst` 가 빈 배열이 되어 시트가 한 장도 안 올라가고,
`TedAbility` 의 `USE_CUBE` 가 false 가 되어 퍼짐 마무리로 갈린다.

**지운 것은 없다.** 시트 4종(`cubeart*` · `cubepx*` · `cubeforge/blast/core` · `cubeburst`),
`scripts/cube/` 전부, 이 문서, `vfx.ts` 의 `FxKey`·`FX_REGISTRY`·`FX_SHEETS` 등록,
`TedAbility` 의 큐브 코드(`startCore`·`lockFlash`·`chargeRings`·`shatter`·`stepShards`·
`startBlast`·`clearNormalPoops`) 전부 그대로다. `character.ts` 도 안 건드렸다.

## 20.5 성능 — 먼저 따졌다

말 10개 × 똥 60개 = **600회 거리 판정/프레임**. 낙하가 동시 4~5개 기준이었으니 2배가 넘는다.

| | 값 |
|---|---|
| `onUpdate` 한 프레임 비용 | **p50 0.038ms · 최대 1.025ms** |
| 한 프레임 최대 똥 반납 | **4개** (타격 이펙트 `maxConcurrent` 6 안) |

## §21 퍼질 때는 머리가 앞선다

낙하는 **발**이 진행 방향 앞이고(`rot = -rad`), 퍼짐은 **머리**가 앞이다.

로컬 위 (0,-1) 은 Phaser 회전 r 에서 `(sin r, -cos r)` 로 간다. 진행 방향을
`(cos θ, sin θ)` 라 하면 `sin r = cos θ`, `-cos r = sin θ` → **`r = θ + π/2`**
(`headAheadRotation`). θ = -90°(위) → r = 0, θ = +90°(아래) → r = 180°.

### 원점 — A 를 골랐다

퍼질 때 머리가 앞서면 발 원점(`FOOT_ORIGIN_Y 0.94`)은 **꽁무니**가 된다. 회전축이
뒤로 가고, `smashPoops` 의 판정 끝점이 보이는 머리보다 말 길이(72px)만큼 뒤처진다.

`scripts/measure-chess-head.py` 로 `chess_96x128.png` 를 실측한 결과:

| | 폰 | … | 킹 |
|---|---|---|---|
| 발 | 0.9375 | 전 프레임 동일 (편차 0) | 0.9375 |
| 머리 | 0.4688 | | 0.0547 |

발은 열 프레임이 완전히 같고 **머리만 0.41 만큼 벌어진다** (표시 크기로 30px).
B(원점은 발에 두고 판정 좌표만 앞으로 밀기)가 싸 보이지만, 밀어야 할 거리가
곧 프레임별 말 길이라 **A 와 똑같은 실측 표가 필요하다.** 표가 같은 값이면
회전축까지 같이 고치는 A 가 낫다 → `HEAD_ORIGIN_Y` 표 + 퍼질 때만 원점 이동.

### 양자화는 안 썼다

말 시트는 96×128 을 54×72 로 **줄여서** 그린다(확대가 아니다). 임의 각도로 돌려도
계단이 안 생기는 것을 `creative/_fx/ted-cube/head_zoom.png` (5배 확대)로 확인했다.
양자화하면 오히려 머리가 진행 방향에서 틀어지므로 기본은 `spreadRotSteps: 0`.
필요하면 8/16 방향으로 바꿀 수 있게 손잡이만 남겼다 (`spreadRotFollow` 도 같이 —
아래로 가는 말이 뒤집히는 게 거슬리면 1 미만으로 낮춘다).

### 회귀

- `[T15]` 판정 끝점이 보이는 머리끝과 일치 (≤ 1px) — 발 원점이면 72px 벌어진다

## §22 순간 렉의 범인 + 말이 화면 밖까지

### 범인 — 파동 텍스처를 발동 프레임에 굽고 있었다

추측하지 않고 하네스에 계측을 넣었다 (프레임별 비용 / 새 오브젝트 수 / 똥 반납 수,
그리고 절차 텍스처가 **언제** 구워지는지).

```
** 연출 도중에 구워진 절차 텍스처 1개 — fx_cubewave(t=592ms)
가장 비싼 프레임: t=592ms  0.777ms   ← 파열이 터지는 바로 그 프레임
```

`cubeWave` 는 절차 생성이라 **첫 재생 때** 캔버스를 만들어 굽는다 — 160×160 × 9장
= 1440×160 캔버스 할당 + 반지름 79px 짜리 radial-gradient 원 18개 채우기 +
`refresh()` 로 0.92MB GPU 업로드. 그게 전부 **파열이 터지는 한 프레임**에 걸렸다.

**고침**: `FX_WARM_GROUPS` + `warmFx()` — 시트를 미리 올릴 때 같이 굽는다.
`preloadFxSheet(scene, 'cubeBurst')` 한 번이 파동까지 구워 두므로 GameScene 은
안 건드렸다. 발동 프레임에 굽는 텍스처 **0개**.

### 범인이 **아니었던** 것 (숫자로 턴다)

| 후보 | 실측 | 판정 |
|---|---|---|
| 판정 600회/프레임 | `onUpdate` p50 **0.009ms** | 아니다 |
| 스프라이트 폭증 | 연출 한 번에 **40개**, 한 프레임 최대 **7개** | 아니다 (풀링 불필요) |
| 똥 대량 회수 | 한 프레임 최대 **8개** (타격 상한 6) | 아니다 |
| 파동 4겹 | 첫 겹 → 마지막 겹 **172ms** 에 분산 | 아니다 |
| 누수 | 5회 반복, 매회 종료 후 **0** | 아니다 |

첫 발동 프레임이 유독 비쌌던 나머지(0.77ms)는 **JIT 워밍업**이다 — 반복 발동에서
0.239 → 0.137ms 로 떨어지고 그 뒤 평평하다.

측정 한계: 하네스의 캔버스는 no-op 이라 **굽는 비용 자체는 못 잰다.** 브라우저가
금지되어 있어 실기 ms 는 확인하지 못했다 — 확인한 것은 "그 일이 그 프레임에
일어난다" 와 "이제 안 일어난다" 두 가지다.

### 말이 화면 밖까지

`spreadDistW: 0.70` 이라 화면 폭의 70% 에서 멈췄다 — 허공에서 사라졌다.

- 사거리 = `hypot(W/2, H/2) + chessHeight` (`spreadReachMul` 로 조절).
  360×640 에서 **457px ≥ 모서리 367px**
- 편차(`spreadReachVar`)는 **위로만** 흔든다. 아래로 흔들면 그 말만 화면 안에서 멈춘다
- 끝에서 줄이고 흐리게 하던 것을 **없앴다.** 화면 밖으로 나가므로 사라지는 연출이 필요 없다
- 화면 밖 + 여유(`spreadCullPad`)를 넘으면 **즉시 회수.** 안 보이는 말을 계속 옮기고
  똥까지 훑지 않는다 → `onUpdate` p50 이 0.034 → **0.009ms**

**파동과의 관계** — 말이 파동을 앞지른다. 그대로 뒀다: 파동은 9프레임 30fps = 300ms 에
알파가 0 이 되고 말은 그 뒤로 300ms 를 더 난다. 둘이 같이 보이는 구간에서는 여전히
파동이 앞서므로 앞지르는 장면이 화면에 없다. 파동을 화면 밖까지 키우면 보이지도
않는 곳의 오버드로만 는다.
