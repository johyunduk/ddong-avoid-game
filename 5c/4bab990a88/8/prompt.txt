### 1. `posHistory` 배열 — **O(n) shift() 문제** (HOT PATH)

**심각도: 중** | **프레임당 호출: 1회**

현재 구현 (line 54-57):
```typescript
this.posHistory.push({ x: api.player.x, y: api.player.y });
if (this.posHistory.length > this.TRAIL_FRAMES) {
  const target = this.posHistory.shift()!;  // ← O(n) 연산!
```

**문제**:
- `shift()`는 배열의 모든 요소를 왼쪽으로 이동시키는 O(n) 연산
- TRAIL_FRAMES = 12이므로, 매 프레임마다 최대 12개 요소를 이동
- 60fps 기준 초당 60회 호출 → 누적 비용 증가

**권장 개선**:
순환 버퍼(Ring Buffer) 패턴으로 O(1)로 개선 가능
```typescript
// 인덱스 기반 순환 구조
private posHistoryBuffer: Array<{ x: number; y: number }> = [];
private historyIndex = 0;

// push 대신
this.posHistoryBuffer[this.historyIndex] = { x: api.player.x, y: api.player.y };
this.historyIndex = (this.historyIndex + 1) % this.TRAIL_FRAMES;

// shift 대신
const target = this.posHistoryBuffer[this.historyIndex];
```

**추정 성능 개선**: 약 50-70% CPU 감소 (배열 크기 12의 shift/unshift 연산 제거)

### 2. `collectSpecialWithGhost` — **Group.getChildren() spread+concat** (점수 이벤트)

**심각도: 낮음** | **호출 빈도: 200점마다 1회** (매우 드문 이벤트)

현재 구현 (line 74-79):
```typescript
const allSpecial = [
  ...api.goldPoops.getChildren(),
  ...api.diamondPoops.getChildren(),
  ...api.topazPoops.getChildren(),
  ...api.rainbowPoops.getChildren(),
```

**분석**:
- 4개 Group에서 각각 `getChildren()` 호출 → 4번의 배열 복사
- spread 연산 `[...arr]` → 4번의 배열 재할당
- concat 동작 3회 (4개 배열 병합)
- filter로 또 다른 배열 순회

**현재 영향도**: **무시할 수 있는 수준**
- 호출 빈도가 200점마다 1회
- 각 Group의 크기가 최대 수십 개 (실시간 낙하 오브젝트)
- 1회 연산 시간 < 1ms (일반적인 모던 브라우저)

**개선 가능성**:
정확한 최적화보다는 **명확성 우선** 권장
```typescript
// 현재 구현도 충분히 명확하고 성능 영향 미미
// 필요시 병합 로직을 명시적으로 작성
const targets: Phaser.Physics.Arcade.Sprite[] = [];
[api.goldPoops, api.diamondPoops, api.topazPoops, api.rainbowPoops].forEach(group => {
  group.getChildren().forEach(p => {
    const sprite = p as Phaser.Physics.Arcade.Sprite;
    if (sprite.active) targets.push(sprite);
  });
});
```
