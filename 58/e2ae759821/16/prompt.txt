### Agent 1: Code Reuse Review

For each change:

2. **Flag any new function that duplicates existing functionality.** Suggest the existing function to use instead.

### Agent 2: Code Quality Review

Review the same changes for hacky patterns:

1. **Redundant state**: state that duplicates existing state, cached values that could be derived, observers/effects that could be direct calls
2. **Parameter sprawl**: adding new parameters to a function instead of generalizing or restructuring existing ones
3. **Copy-paste with slight variation**: near-duplicate code blocks that should be unified with a shared abstraction
4. **Leaky abstractions**: exposing internal details that should be encapsulated, or breaking existing abstraction boundaries
5. **Stringly-typed code**: using raw strings where constants, enums (string unions), or branded types already exist in the codebase
6. **Unnecessary JSX nesting**: wrapper Boxes/elements that add no layout value — check if inner component props (flexShrink, alignItems, etc.) already provide the needed behavior
7. **Unnecessary comments**: comments explaining WHAT the code does (well-named identifiers already do that), narrating the change, or referencing the task/caller — delete; keep only non-obvious WHY (hidden constraints, subtle invariants, workarounds)

### Agent 3: Efficiency Review

Review the same changes for efficiency:

1. **Unnecessary work**: redundant computations, repeated file reads, duplicate network/API calls, N+1 patterns
2. **Missed concurrency**: independent operations run sequentially when they could run in parallel
3. **Hot-path bloat**: new blocking work added to startup or per-request/per-render hot paths
4. **Recurring no-op updates**: state/store updates inside polling loops, intervals, or event handlers that fire unconditionally — add a change-detection guard so downstream consumers aren't notified when nothing changed. 5. **Unnecessary existence checks**: pre-checking file/resource existence before operating (TOCTOU anti-pattern) — operate directly and handle the error
6. **Memory**: unbounded data structures, missing cleanup, event listener leaks
7. **Overly broad operations**: reading entire files when only a portion is needed, loading all items when filtering for one

Here are the findings, item by item:

**1. `_updateDebugText()` — unnecessary calls**

No real issue. It's called twice total per tail acquisition (once in `_addTail`, once if invincibility triggers immediately after the 9th tail, from `_endInvincibility`). It's also called once on invincibility end. The cost is a single `setText` on a Phaser Text object, which is cheap. There is no path where it's called with unchanged content — each call site represents a state change. No fix needed.

**2. `_updateTailPositions()` — missing early exit when `tails.length === 0`**

This is a real, cheap optimization worth adding. Every frame, even before the first tail is earned (score 0–149), the method is called, enters the `for (const tail of this.tails)` loop body, and immediately exits because `this.tails` is empty — but `scene.time.now * 0.001`, `player.x`, and `player.y` are still read unnecessarily. More importantly, once invincibility ends, `this.tails` is reset to `[]` and `tailCount` to `0`, but `_updateTailPositions` keeps running every frame for the rest of the game. Adding `if (this.tails.length === 0) return;` at the top of `_updateTailPositions` eliminates all of that overhead with one line:

```typescript
private _updateTailPositions(api: GameSceneAPI): void {
  if (this.tails.length === 0) return;   // ← add this
  ...
}
```

**3. `getSpawnCountReduction()` — no-reset approach**

Intentional and correct. `spawnReduction` represents a permanent passive that accumulates as 3rd/6th/9th tails are added and is zeroed in `_endInvincibility` along with all other tail state. GameScene reads it every spawn tick via `ability.getSpawnCountReduction()` and applies it as a live subtraction from `poopCount`. There is no double-application risk. No issue.

**4. `Player.addPermanentSpeed()` — no issues**

The implementation is correct. It updates `baseSpeed` and immediately recalculates `speed` respecting the speed boost multiplier. No issue.

**5. `debugText` memory leak on scene restart**

This is a real bug. The scene restart path (`scene.restart(...)`) triggers Phaser's `shutdown` event, which destroys all scene game objects — but `debugText` is a Phaser `Text` object added to the scene, so Phaser will destroy it automatically on shutdown. However, `GumiAbility.debugText` still holds the (now-dead) reference, and critically, `onDestroy` is **not called** on the restart path.

Looking at the code:
- `onDestroy` is called explicitly in `hitPoop` (game over) and `handleCheatDetected` — but **not** on `scene.restart()`.
- On restart, Phaser destroys the scene's display list (including `debugText`), then calls `init` → `create`. `ability.onCreate` runs again, creating a new `debugText` — but `onDestroy` was never called, so `tails`' segment images are also leaked (they were on the old scene's display list, so Phaser destroys them, but `this.tails` array is never cleared, meaning stale `TailObj` references persist into the new game session).

The actual leak: after a restart, `this.tails` contains `TailObj` entries whose `si.img` objects are destroyed Phaser objects. If the player earns tails again in the new session, `_updateTailPositions` iterates the stale tails from the previous session (their `si.img.active` will be `false` so the `setPosition` call is skipped, but the objects are still iterated). More dangerously, `_endInvincibility` calls `si.img.destroy()` on them again (double-destroy).

The fix is to hook the scene's `shutdown` event in `onCreate` and call `onDestroy` from it:

```typescript
override onCreate(api: GameSceneAPI): void {
  api.player.setDepth(5);
  // ... debugText setup ...
  api.scene.events.once('shutdown', () =&gt; this.onDestroy(api));
}
```

Or alternatively, reset `this.tails = []` and null `this.debugText` in `onCreate` before creating new objects (so that a second `onCreate` after restart doesn't operate on stale state). The shutdown-hook approach is cleaner and consistent with how GameScene already handles other `shutdown` cleanup.
